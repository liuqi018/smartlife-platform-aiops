# Docker 容器 OOMKilled 排查

## 1. 问题概述

Docker 容器 `OOMKilled` 是指容器中的进程因内存不足，被 Linux 内核的 OOM Killer 或 Cgroup 内存控制机制强制终止。

Docker 容器可以设置独立的内存限制。即使宿主机仍然存在可用内存，只要容器的内存使用量达到自身限制，容器中的进程仍可能被终止。

容器发生 OOM 后，通常会出现：

```text
OOMKilled=true
```

容器退出码通常为：

```text
137
```

退出码 `137` 表示进程收到 `SIGKILL` 信号。OOM 是常见原因之一，但并不是唯一原因，也可能是管理员、脚本或其他系统主动执行了强制终止。因此，需要结合 `OOMKilled`、Docker 事件和宿主机内核日志进行确认。

容器 OOMKilled 排查的核心目标包括：

1. 确认容器是否因 OOM 被终止。
2. 确认是容器达到内存限制，还是宿主机整体内存不足。
3. 查看容器内存限制和实际使用量。
4. 定位容器内高内存进程。
5. 区分正常容量不足和内存泄漏。
6. 调整应用、容器和宿主机内存配置。
7. 建立内存监控和 OOM 告警机制。

## 2. 常见问题现象

Docker 容器发生 OOMKilled 时，通常会出现以下现象：

1. 容器突然退出。
2. 容器退出码为 `137`。
3. `docker inspect` 显示 `OOMKilled=true`。
4. 容器配置了重启策略后频繁重启。
5. 应用日志突然中断，没有完整异常信息。
6. Java 应用可能没有输出 `OutOfMemoryError`。
7. 容器内存使用量长期接近限制。
8. 宿主机内核日志出现 OOM Killer 信息。
9. 业务接口突然不可用。
10. 容器重启后暂时恢复。
11. 批量任务或流量高峰时容易发生。
12. 容器中无法创建新线程或分配内存。
13. 宿主机 Swap 使用率持续升高。
14. 多个容器在相近时间被终止。
15. 数据库、缓存或 Java 服务反复退出。

常见状态如下：

```text
Exited (137)
```

```text
OOMKilled: true
```

内核日志可能包含：

```text
Out of memory: Killed process 12345 (java)
```

## 3. OOMKilled 的常见原因

### 3.1 容器内存限制过小

应用正常运行所需内存超过容器限制，导致容器被强制终止。

例如，容器限制为：

```text
1GB
```

但应用实际需要：

```text
1.5GB
```

此时即使宿主机拥有大量可用内存，容器仍可能发生 OOMKilled。

### 3.2 应用存在内存泄漏

应用不断申请内存，但对象、缓存、缓冲区或本地内存没有正确释放，导致容器内存持续增长。

常见原因包括：

- Java 堆对象泄漏。
- 本地缓存没有容量限制。
- ThreadLocal 没有清理。
- 队列持续堆积。
- 直接内存泄漏。
- C 或 C++ 本地内存没有释放。
- Python 对象和集合持续增长。
- 连接和文件资源没有关闭。

### 3.3 Java 堆配置接近容器上限

例如，容器内存限制为 2GB，同时配置：

```bash
-Xmx2g
```

Java 进程除堆内存外，还需要使用：

- 元空间。
- 直接内存。
- 线程栈。
- Code Cache。
- GC 本地数据结构。
- JNI 和本地库内存。

因此，Java 最大堆内存不能直接设置为容器内存上限。

### 3.4 大文件或批量任务

应用一次性读取大量文件、数据库结果或消息，可能形成短时间内存峰值。

常见场景包括：

- 大文件上传和解析。
- Excel 或 PDF 全量加载。
- 数据库查询没有分页。
- 批量导入或导出。
- 图片和视频处理。
- 消息批量大小过大。
- 多个任务同时执行。

### 3.5 线程数量过多

每个线程都会占用线程栈和其他本地内存。容器中线程数量持续增加时，可能在 Java 堆尚未耗尽前触发容器 OOM。

### 3.6 宿主机整体内存不足

如果宿主机上多个容器和进程共同耗尽物理内存，Linux 内核可能从所有进程中选择一个高评分进程终止。

这种情况下，不一定是目标容器自身达到限制，而是宿主机整体发生系统级 OOM。

### 3.7 容器未设置内存限制

容器没有设置内存限制时，可以持续占用宿主机内存，最终可能导致宿主机整体 OOM，并影响其他容器和系统进程。

### 3.8 Swap 不足或未配置

Swap 可以缓解短时间内存峰值。如果宿主机没有 Swap，或者 Swap 已经耗尽，系统在物理内存不足时更容易触发 OOM。

Swap 只能作为缓冲手段，不能代替内存泄漏修复或物理内存扩容。

## 4. 排查前的注意事项

发生 OOMKilled 后，不要立即删除容器或清理日志。

应优先保存：

1. 容器状态。
2. 容器退出码。
3. `OOMKilled` 状态。
4. 容器内存限制。
5. 容器日志。
6. Docker 事件。
7. 宿主机内核日志。
8. 宿主机内存和 Swap 状态。
9. 应用内存配置。
10. 问题发生时的任务和流量信息。

建议执行：

```bash
docker inspect <容器名称或ID>
docker logs --timestamps --tail 500 <容器名称或ID>
docker events --since 30m
free -h
swapon --show
dmesg -T | tail -200
```

## 5. 第一步：确认是否发生 OOMKilled

执行：

```bash
docker inspect <容器名称或ID> \
  --format '{{.State.OOMKilled}}'
```

如果输出：

```text
true
```

说明 Docker 记录该容器曾因 OOM 被终止。

查看退出码：

```bash
docker inspect <容器名称或ID> \
  --format '{{.State.ExitCode}}'
```

查看完整状态：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .State}}'
```

需要重点记录：

- `OOMKilled`。
- `ExitCode`。
- `Error`。
- `StartedAt`。
- `FinishedAt`。
- `Restarting`。
- `RestartCount`。

## 6. 第二步：查看容器日志

执行：

```bash
docker logs --timestamps --tail 500 <容器名称或ID>
```

重点查看退出前是否出现：

```text
OutOfMemoryError
Cannot allocate memory
unable to create new native thread
Direct buffer memory
Killed
```

容器被 Cgroup 直接强制终止时，应用可能来不及写入异常信息。因此，没有 OOM 日志并不能排除 OOMKilled。

如果 Java 日志中出现：

```text
java.lang.OutOfMemoryError
```

说明 JVM 内部某个内存区域已经发生 OOM。

如果没有 Java OOM，但容器 `OOMKilled=true`，更可能是 Java 进程总内存超过容器限制。

## 7. 第三步：查看容器内存限制

查看内存限制：

```bash
docker inspect <容器名称或ID> \
  --format '{{.HostConfig.Memory}}'
```

查看内存和 Swap 限制：

```bash
docker inspect <容器名称或ID> \
  --format 'Memory={{.HostConfig.Memory}} MemorySwap={{.HostConfig.MemorySwap}}'
```

结果通常以字节为单位。

查看容器配置：

```bash
docker inspect <容器名称或ID> | less
```

如果 `Memory` 为 `0`，通常表示没有设置明确的容器内存上限，容器可能使用宿主机允许的内存。

Docker Compose 中可以根据实际部署方式配置资源限制。需要确认当前 Compose 模式是否真正应用了对应配置，而不能只看 YAML 文件内容。

## 8. 第四步：查看容器实时内存

容器仍然运行时执行：

```bash
docker stats
```

只查看指定容器：

```bash
docker stats <容器名称或ID>
```

重点关注：

- `MEM USAGE`。
- `LIMIT`。
- `MEM %`。
- `CPU %`。
- `PIDS`。

如果内存使用量持续增长并接近限制，应重点怀疑：

- 内存泄漏。
- 缓存持续增长。
- 队列堆积。
- 批量任务。
- 线程数量增加。
- 堆外内存增长。

`docker stats` 只能查看当前或实时状态。如果容器已经退出，需要依赖历史监控确认 OOM 前的内存趋势。

## 9. 第五步：查看 Docker 事件

执行：

```bash
docker events --since 30m
```

只查看指定容器：

```bash
docker events \
  --since 30m \
  --filter container=<容器名称或ID>
```

重点关注：

```text
oom
die
kill
restart
start
```

通过事件时间可以还原：

```text
内存达到上限
    ↓
发生 OOM
    ↓
主进程退出
    ↓
容器停止
    ↓
重启策略重新启动容器
```

## 10. 第六步：查看宿主机 OOM 日志

执行：

```bash
dmesg -T | grep -iE 'out of memory|oom|killed process'
```

使用 systemd 的系统可以执行：

```bash
journalctl -k | grep -iE 'out of memory|oom|killed process'
```

查看指定时间范围：

```bash
journalctl -k \
  --since "2026-07-21 10:00:00" \
  --until "2026-07-21 11:00:00"
```

重点确认：

- 被终止的进程名称。
- 进程 PID。
- OOM 发生时间。
- 进程内存占用。
- 是否为容器 Cgroup OOM。
- 是否为宿主机整体 OOM。
- 是否有多个进程同时被终止。

## 11. 第七步：检查宿主机内存

执行：

```bash
free -h
```

查看 Swap：

```bash
swapon --show
```

观察内存换页：

```bash
vmstat 1 10
```

查看高内存进程：

```bash
ps -eo pid,user,%mem,rss,vsz,cmd \
  --sort=-rss | head -20
```

如果宿主机 `MemAvailable` 很低、Swap 已经耗尽，并且多个容器同时出现异常，可能是宿主机整体内存不足。

如果宿主机内存充足，但单个容器发生 OOMKilled，则应重点检查该容器自身的内存限制和应用内存使用。

## 12. 第八步：定位容器内高内存进程

容器仍然运行时执行：

```bash
docker top <容器名称或ID>
```

进入容器：

```bash
docker exec -it <容器名称或ID> sh
```

查看进程：

```bash
ps aux --sort=-%mem
```

部分精简镜像中可能没有完整的 `ps` 工具，可以从宿主机通过容器 PID 排查。

查看容器主进程宿主机 PID：

```bash
docker inspect <容器名称或ID> \
  --format '{{.State.Pid}}'
```

然后查看：

```bash
cat /proc/<宿主机PID>/status
```

重点关注：

```text
VmRSS
VmSize
VmSwap
Threads
```

## 13. Java 容器 OOMKilled 排查

查看 Java 启动参数：

```bash
docker exec <容器名称或ID> \
  jcmd 1 VM.flags
```

查看启动命令：

```bash
docker exec <容器名称或ID> \
  jcmd 1 VM.command_line
```

重点关注：

```text
-Xms
-Xmx
-Xss
-XX:MaxMetaspaceSize
-XX:MaxDirectMemorySize
-XX:MaxRAMPercentage
```

Java 容器总内存大致包括：

```text
Java Heap
+ Metaspace
+ Direct Memory
+ Thread Stack
+ Code Cache
+ GC Native Memory
+ JNI 与本地库
```

不能直接设置：

```text
容器限制 = 2GB
-Xmx = 2GB
```

应根据应用堆外内存和线程数量预留合理空间。

## 14. Java 堆内存排查

如果容器没有立即退出，可以执行：

```bash
docker exec <容器名称或ID> \
  jcmd 1 GC.heap_info
```

查看 GC：

```bash
docker exec <容器名称或ID> \
  jstat -gcutil 1 1000 10
```

建议提前配置：

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump
```

Heap Dump 目录应挂载到宿主机或持久化数据卷，并确保有足够磁盘空间。

需要注意，容器级 OOMKilled 可能不会触发 JVM 的 `HeapDumpOnOutOfMemoryError`，因为 JVM 可能没有抛出 Java OOM，而是被内核直接终止。

## 15. 堆外内存排查

如果 Java 堆使用率不高，但容器总内存持续增长，应重点检查：

- DirectByteBuffer。
- Netty 直接内存。
- 线程栈。
- 元空间。
- JNI 本地库。
- 内存映射文件。
- Code Cache。
- JVM 本地数据结构。

如果启动时启用了 Native Memory Tracking，可以执行：

```bash
docker exec <容器名称或ID> \
  jcmd 1 VM.native_memory summary
```

查看 DirectByteBuffer：

```bash
docker exec <容器名称或ID> \
  jcmd 1 GC.class_histogram | grep DirectByteBuffer
```

Java Heap Dump 不能完整反映堆外内存，因此不能只分析 Heap Dump。

## 16. 线程数量排查

查看容器 PID 数量：

```bash
docker stats
```

查看 Java 线程数量：

```bash
docker exec <容器名称或ID> \
  sh -c 'ls /proc/1/task | wc -l'
```

线程数量过多会消耗线程栈和本地内存。

常见原因包括：

- 每个请求创建线程。
- 线程池重复创建。
- 线程泄漏。
- 大量线程阻塞。
- 定时任务重复注册。
- `-Xss` 设置过大。

## 17. 大文件和批量任务排查

如果 OOMKilled 发生在固定任务期间，应检查：

- 是否一次性读取大文件。
- 数据库查询是否分页。
- 单批消息数量是否过多。
- 并发任务数量是否过高。
- 是否同时保留多个数据副本。
- 上传文件大小是否有限制。
- 是否存在大数组或大集合。
- 是否执行图片、视频或 PDF 处理。

优化方向包括：

- 流式读取。
- 分页查询。
- 分批处理。
- 降低并发。
- 限制文件大小。
- 及时释放对象引用。
- 将重型任务放入独立容器。
- 设置独立资源限制。

## 18. 容器内存与 Swap

Docker 容器可以受到内存和内存加 Swap 的联合限制。

查看：

```bash
docker inspect <容器名称或ID> \
  --format 'Memory={{.HostConfig.Memory}} MemorySwap={{.HostConfig.MemorySwap}}'
```

具体行为会受到 Docker 配置、Cgroup 版本和宿主机 Swap 状态影响。

Swap 可以缓解短时内存峰值，但会增加磁盘 IO 和应用延迟。对于延迟敏感服务，不能依赖 Swap 解决长期内存不足。

## 19. 临时处理措施

容器 OOMKilled 已影响业务时，可以采取：

1. 保存容器状态、日志和 Docker 事件。
2. 提高容器内存限制。
3. 降低 Java 最大堆内存。
4. 暂停大文件和批量任务。
5. 降低消息消费并发度。
6. 对高内存接口进行限流。
7. 将流量切换到健康实例。
8. 增加容器副本分担流量。
9. 暂停异常增长的本地缓存。
10. 保存现场后重新创建容器。
11. 为宿主机增加物理内存或 Swap。
12. 对非核心任务进行降级。

临时增加内存只能恢复服务，不能代替内存泄漏和程序逻辑排查。

## 20. 永久解决方案

### 20.1 合理设置容器内存

容器限制应覆盖应用正常内存、启动峰值和必要安全余量。

### 20.2 合理设置 JVM 参数

Java 最大堆应小于容器总内存，并为堆外内存预留空间。具体比例应通过监控和压力测试确定。

### 20.3 修复内存泄漏

- 限制本地缓存。
- 清理 ThreadLocal。
- 修复对象长期引用。
- 限制队列长度。
- 关闭未释放资源。
- 修复直接内存泄漏。
- 控制线程数量。

### 20.4 优化数据处理

- 大文件流式处理。
- 数据库分页查询。
- 批量任务分批执行。
- 降低并发度。
- 限制单次请求数据量。
- 避免同时保存多个数据副本。

### 20.5 隔离高内存任务

将报表、文件解析、图片处理和大批量任务部署到独立容器，避免影响在线接口。

## 21. 不建议直接执行的操作

### 21.1 不建议只提高内存限制

如果存在内存泄漏，提高限制只会延迟下一次 OOMKilled。

### 21.2 不建议只减小 Java 堆

堆设置过小可能导致频繁 Full GC 或 Java Heap OOM。应基于堆内和堆外内存实际占用调整。

### 21.3 不建议立即删除容器

删除容器前应保存日志、退出码、`inspect` 和事件信息。

### 21.4 不建议将宿主机全部内存分配给容器

需要为操作系统、Docker 守护进程、文件缓存和其他容器预留空间。

### 21.5 不建议无限自动重启

容器反复 OOM 和重启会持续影响业务，并可能反复执行初始化任务。

## 22. 监控与预防建议

建议监控以下指标：

- 容器内存使用量。
- 容器内存使用率。
- 容器内存限制。
- Working Set。
- Cache。
- RSS。
- Swap 使用量。
- OOMKilled 次数。
- 容器重启次数。
- Java 堆使用量。
- Java 堆外内存。
- Full GC 次数。
- 线程数量。
- 本地缓存数量。
- 任务队列长度。
- 宿主机可用内存。
- 宿主机 Swap。
- 宿主机 OOM 事件。

推荐告警条件包括：

- 容器内存连续超过限制的 80%。
- 容器内存持续增长且不回落。
- 出现 OOMKilled。
- 容器退出码为 137。
- 容器重启次数增加。
- Java 堆不高但容器 RSS 持续增长。
- 线程数量异常增加。
- 宿主机 `MemAvailable` 持续偏低。
- 多个容器同时接近内存限制。

## 23. 推荐排查流程

Docker 容器 OOMKilled 可以按照以下顺序排查：

1. 使用 `docker inspect` 确认 `OOMKilled`。
2. 查看容器退出码是否为 137。
3. 保存容器日志和 Docker 事件。
4. 查看容器内存和 Swap 限制。
5. 查看历史内存监控趋势。
6. 查看宿主机内核 OOM 日志。
7. 区分容器 OOM 与宿主机 OOM。
8. 检查宿主机内存、Swap 和高内存进程。
9. 定位容器内高内存进程。
10. 如果是 Java 应用，检查堆和堆外内存。
11. 检查线程数量、缓存和任务队列。
12. 检查是否存在大文件或批量任务。
13. 采取限流、暂停任务、扩容或重启等临时措施。
14. 修复内存泄漏和无界数据结构。
15. 合理调整容器与 JVM 内存配置。
16. 使用压力测试验证峰值内存。
17. 建立容器内存和 OOMKilled 监控。

## 24. 常用排查命令汇总

```bash
# 查看容器状态
docker ps -a

# 查看是否 OOMKilled
docker inspect <容器名称或ID> \
  --format '{{.State.OOMKilled}}'

# 查看退出码
docker inspect <容器名称或ID> \
  --format '{{.State.ExitCode}}'

# 查看完整状态
docker inspect <容器名称或ID> \
  --format '{{json .State}}'

# 查看容器日志
docker logs --timestamps --tail 500 <容器名称或ID>

# 查看内存和 Swap 限制
docker inspect <容器名称或ID> \
  --format 'Memory={{.HostConfig.Memory}} MemorySwap={{.HostConfig.MemorySwap}}'

# 查看实时资源
docker stats <容器名称或ID>

# 查看 Docker 事件
docker events --since 30m \
  --filter container=<容器名称或ID>

# 查看容器主进程 PID
docker inspect <容器名称或ID> \
  --format '{{.State.Pid}}'
```

## 25. 排查结论模板

### 故障现象

Java 应用容器在业务高峰期突然退出，Docker 自动重启容器后暂时恢复，随后再次发生相同问题。

### 故障确认

通过 `docker inspect` 确认容器退出码为 137，且 `OOMKilled=true`。容器内存限制为 2GB，历史监控显示退出前内存使用量已经达到上限。

### 根本原因

Java 最大堆配置为 `-Xmx2g`，没有为元空间、直接内存、线程栈和 JVM 本地内存预留空间。业务高峰期线程数量和直接内存增加，导致进程总内存超过容器限制，被 Cgroup 强制终止。

### 临时处理

适当提高容器内存限制，降低 Java 最大堆配置，并滚动重新创建容器，恢复业务服务。

### 永久修复

根据 Heap、Metaspace、Direct Memory 和线程栈的实际占用重新规划容器内存；限制线程池大小和任务队列长度；增加 Java 堆、堆外内存和容器 RSS 监控。

### 验证结果

修复后进行相同业务压力测试，容器总内存保持在限制范围内，未再出现 OOMKilled，容器重启次数保持不变。

## 26. 总结

Docker 容器 OOMKilled 排查的第一步是通过 `docker inspect` 确认 `OOMKilled` 状态，并结合退出码、Docker 事件和宿主机内核日志判断具体原因。

容器 OOM 可能由容器限制过小、应用内存泄漏、Java 堆配置不合理、大文件处理、线程过多或宿主机整体内存不足引起。宿主机仍有可用内存并不代表容器不会 OOM，只要容器达到自身 Cgroup 限制，进程仍然可能被终止。

对于 Java 容器，不能将 `-Xmx` 直接设置为容器内存上限。必须为元空间、直接内存、线程栈、Code Cache 和 JVM 本地内存预留足够空间。

增加容器内存只能缓解容量不足，不能解决内存泄漏。永久解决方案应结合应用内存分析、容器资源规划、任务限流和压力测试，并建立容器内存、重启次数和 OOMKilled 监控。
