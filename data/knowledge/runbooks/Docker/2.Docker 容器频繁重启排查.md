# Docker 容器频繁重启排查

## 1. 问题概述

Docker 容器频繁重启是指容器启动后运行较短时间便退出，随后又被 Docker 重启策略、Docker Compose 或外部编排系统重新启动，形成反复退出和重启的循环。

容器本质上依赖一个前台主进程维持运行。当主进程退出时，容器就会停止。如果容器配置了 `always`、`unless-stopped` 或 `on-failure` 等重启策略，Docker 会尝试重新启动该容器。

容器频繁重启通常不是 Docker 重启策略本身的问题，而是容器主进程持续异常退出。常见原因包括：

1. 应用程序启动失败。
2. 配置文件或环境变量错误。
3. 数据库、Redis 等依赖服务不可用。
4. 容器发生 OOM。
5. 健康检查失败。
6. 主进程执行结束。
7. 文件或目录权限不足。
8. 数据卷挂载错误。
9. 端口冲突。
10. 应用发生崩溃或段错误。
11. Docker 守护进程或宿主机异常。
12. 外部脚本或运维系统主动重启容器。

排查的核心是确认容器为什么退出、由谁重新启动，以及每次退出前发生了什么。

## 2. 常见问题现象

容器频繁重启时，通常会出现以下现象：

1. `docker ps` 中容器状态显示 `Restarting`。
2. 容器启动时间不断变化。
3. `RestartCount` 持续增加。
4. 服务端口时而存在、时而消失。
5. 应用日志反复打印启动过程。
6. 数据库迁移或初始化任务重复执行。
7. 业务接口间歇性可用。
8. 日志中不断出现相同异常。
9. 容器退出码长期固定为某个值。
10. 容器状态显示 `OOMKilled`。
11. Docker 事件中反复出现 `die`、`start` 和 `restart`。
12. 宿主机 CPU、内存或磁盘使用率异常。
13. 应用在依赖服务未就绪时启动失败。
14. 健康检查持续失败。
15. 容器重启后短暂恢复，随后再次退出。

容器频繁重启可能造成请求中断、任务重复执行、数据状态异常和依赖服务压力升高，因此应尽快保留日志和退出现场。

## 3. 常见产生原因

### 3.1 应用程序启动异常

应用启动过程中发生未捕获异常，主进程返回非零退出码，容器随之退出。

常见原因包括：

- 配置文件格式错误。
- 环境变量缺失。
- 数据库连接失败。
- 端口绑定失败。
- 程序依赖缺失。
- 启动参数错误。
- 数据库初始化失败。
- 证书或密钥读取失败。

### 3.2 内存不足

容器内存使用量达到限制后，进程可能被 Cgroup 强制终止。容器退出码通常为 `137`，并且 `OOMKilled` 可能显示为 `true`。

Java 应用如果将 `-Xmx` 设置得接近容器内存上限，没有为元空间、直接内存和线程栈预留空间，容易发生容器 OOM。

### 3.3 主进程正常执行结束

容器中的主进程如果属于一次性任务，或者启动脚本将应用放入后台后自身退出，容器也会结束。

例如：

```bash
java -jar app.jar &
```

脚本执行结束后，容器不会因为后台进程存在而继续保持正常运行。容器主进程应在前台运行。

### 3.4 依赖服务不可用

应用启动时强依赖 MySQL、Redis、Kafka、配置中心或注册中心。如果依赖尚未就绪，应用可能立即退出，然后被重启策略再次拉起。

### 3.5 健康检查失败

Docker 原生健康检查失败通常只会将容器标记为 `unhealthy`，不一定由 Docker 自动重启。但 Docker Compose 之外的外部监控脚本、编排平台或服务管理系统可能在健康检查失败后主动重启容器。

因此，需要区分：

- 容器主进程主动退出。
- Docker 重启策略触发。
- 外部系统因健康检查失败主动重启。

### 3.6 数据卷和权限问题

容器运行用户没有权限读取配置或写入数据目录，应用可能在启动或运行期间异常退出。

### 3.7 程序崩溃

C、C++、JNI 或其他本地库发生段错误时，容器主进程可能以退出码 `139` 退出。

### 3.8 Docker 守护进程或宿主机重启

Docker 服务重启、宿主机重启或系统升级后，配置了自动重启策略的容器会重新启动。需要判断这是一次正常重启，还是持续重复发生。

## 4. 排查前的注意事项

排查时应注意：

1. 不要立即删除故障容器。
2. 不要只执行 `docker restart`。
3. 保存日志、退出码和 `inspect` 结果。
4. 不要直接取消重启策略后忽略根因。
5. 不要随意删除数据卷。
6. 不要通过 `chmod -R 777` 处理所有权限问题。
7. 应确认是否有外部系统控制容器。
8. 应记录每次退出和重启时间。
9. 日志滚动较快时应及时保存。
10. 修改配置后通常需要重新创建容器。

建议先执行：

```bash
docker ps -a
docker inspect <容器名称或ID>
docker logs --timestamps --tail 500 <容器名称或ID>
docker events --since 30m
free -h
df -hT
```

## 5. 第一步：查看容器状态

执行：

```bash
docker ps -a
```

重点关注：

- `STATUS`。
- 退出码。
- 启动时间。
- 容器名称。
- 镜像版本。
- 是否显示 `Restarting`。
- 是否显示 `unhealthy`。

查看状态详情：

```bash
docker inspect <容器名称或ID> --format '{{json .State}}'
```

该结果通常包含：

- `Status`。
- `Running`。
- `Restarting`。
- `OOMKilled`。
- `Dead`。
- `ExitCode`。
- `Error`。
- `StartedAt`。
- `FinishedAt`。
- `Health`。

## 6. 第二步：查看重启次数和策略

查看重启次数：

```bash
docker inspect <容器名称或ID> --format '{{.RestartCount}}'
```

查看重启策略：

```bash
docker inspect <容器名称或ID> --format '{{json .HostConfig.RestartPolicy}}'
```

常见策略包括：

- `no`：不自动重启。
- `on-failure`：进程异常退出时重启。
- `always`：容器退出后自动重启。
- `unless-stopped`：除非被主动停止，否则自动重启。

重启策略只负责重新拉起容器，不能解决应用持续退出的问题。如果容器每次启动后都立即退出，重启策略会形成无限重启循环。

## 7. 第三步：查看容器日志

执行：

```bash
docker logs --timestamps --tail 500 <容器名称或ID>
```

实时查看：

```bash
docker logs -f <容器名称或ID>
```

重点查看每次退出前的最后几行：

```text
error
fatal
exception
permission denied
connection refused
timeout
out of memory
address already in use
segmentation fault
```

如果日志中反复出现完整启动日志，说明应用每次被重新启动后都执行了初始化流程。

如果没有任何日志，应重点检查：

- `ENTRYPOINT` 或 `CMD` 是否存在。
- 启动脚本是否有执行权限。
- 脚本解释器是否存在。
- 镜像架构是否兼容。
- 主进程是否在日志初始化前退出。
- 日志是否写入容器内部文件。

## 8. 第四步：检查退出码

查看退出码：

```bash
docker inspect <容器名称或ID> --format '{{.State.ExitCode}}'
```

常见退出码如下：

| 退出码 | 常见含义                     |
| ------ | ---------------------------- |
| `0`    | 主进程正常执行结束           |
| `1`    | 应用程序一般性错误           |
| `126`  | 命令存在但无法执行           |
| `127`  | 启动命令不存在               |
| `137`  | 收到 `SIGKILL`，可能发生 OOM |
| `139`  | 发生段错误                   |
| `143`  | 收到 `SIGTERM`               |

退出码只能作为线索，最终还需要结合日志、`OOMKilled`、Docker 事件和宿主机日志确认。

## 9. 第五步：检查是否发生 OOM

查看 OOM 状态：

```bash
docker inspect <容器名称或ID> --format '{{.State.OOMKilled}}'
```

查看内存限制：

```bash
docker inspect <容器名称或ID> --format '{{.HostConfig.Memory}}'
```

查看资源使用：

```bash
docker stats
```

查看宿主机 OOM 日志：

```bash
dmesg -T | grep -iE 'out of memory|oom|killed process'
```

如果 `OOMKilled=true`，应继续检查：

- 容器内存限制是否过小。
- 应用是否存在内存泄漏。
- 启动阶段是否加载大量数据。
- Java 堆是否接近容器内存上限。
- 是否存在大量线程或直接内存。
- 宿主机整体内存是否不足。

## 10. 第六步：查看 Docker 事件

执行：

```bash
docker events --since 30m
```

只查看指定容器：

```bash
docker events \
  --since 30m \
  --filter container=<容器名称或ID>
```

重点关注：

```text
start
die
restart
kill
oom
health_status
stop
```

Docker 事件可以帮助还原：

```text
容器启动 → 健康检查失败 → 容器被终止 → 容器重新启动
```

如果事件中出现 `kill`，应继续确认信号来源，是 Docker、管理员、脚本还是外部平台主动终止。

## 11. 第七步：检查启动命令和主进程

查看启动命令：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .Config.Entrypoint}} {{json .Config.Cmd}}'
```

常见问题包括：

- 启动命令路径错误。
- Docker Compose 的 `command` 覆盖镜像命令。
- 脚本将服务放入后台。
- 启动脚本执行完毕后正常退出。
- Shell 脚本没有使用 `exec` 启动主进程。
- 程序收到信号后没有正确处理。
- 一次性任务错误配置为长期服务。

推荐脚本形式：

```bash
exec java -jar app.jar
```

使用 `exec` 可以让应用进程替代 Shell 成为容器主进程，更正确地接收 Docker 发送的终止信号。

## 12. 第八步：检查环境变量和配置

查看环境变量：

```bash
docker inspect <容器名称或ID> --format '{{json .Config.Env}}'
```

检查 Compose 最终配置：

```bash
docker compose config
```

重点检查：

- 数据库地址和端口。
- Redis 地址。
- 用户名和密码。
- 应用运行环境。
- 配置文件路径。
- 证书和密钥路径。
- `.env` 文件是否正确加载。
- 变量值是否包含错误引号或空格。
- 生产和测试配置是否混用。

如果应用启动时读取不到关键配置，可能每次启动后立即退出。

## 13. 第九步：检查依赖服务

进入相同网络的临时容器进行测试：

```bash
docker run --rm \
  --network <网络名称> \
  busybox nslookup <服务名称>
```

测试端口：

```bash
docker run --rm \
  --network <网络名称> \
  busybox nc -vz <服务名称> <端口>
```

检查容器网络：

```bash
docker network inspect <网络名称>
```

常见问题包括：

- 依赖服务尚未启动。
- 服务名称错误。
- 容器不在同一个网络。
- 使用 `127.0.0.1` 访问其他容器。
- 数据库拒绝连接。
- 依赖服务启动时间较长。
- 应用没有重试或等待机制。

Docker Compose 中的 `depends_on` 主要控制启动顺序，不一定表示依赖服务已经完成业务初始化。应用仍应配置合理的连接重试和退避机制。

## 14. 第十步：检查健康检查

查看健康检查配置：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .Config.Healthcheck}}'
```

查看健康检查结果：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .State.Health}}'
```

常见问题包括：

- 健康检查路径错误。
- 健康检查端口错误。
- 工具不存在，例如镜像中没有 `curl`。
- `start_period` 太短。
- 应用启动时间较长。
- 健康检查超时时间过短。
- 健康接口依赖下游服务。
- 外部系统在 `unhealthy` 后主动重启容器。

健康检查应尽量验证应用自身是否能够提供基本服务，避免将非关键下游异常直接等同于容器必须重启。

## 15. 第十一步：检查挂载和权限

查看挂载：

```bash
docker inspect <容器名称或ID> --format '{{json .Mounts}}'
```

查看容器运行用户：

```bash
docker inspect <容器名称或ID> --format '{{.Config.User}}'
```

检查宿主机目录：

```bash
ls -ld /宿主机/挂载目录
```

常见问题包括：

- 配置文件挂载路径错误。
- 数据目录不可写。
- 日志目录不可写。
- 宿主机文件不存在。
- 文件和目录类型不匹配。
- 容器 UID、GID 与宿主机权限不一致。
- SELinux 阻止访问。
- 挂载后覆盖了镜像内原有文件。

权限调整应遵循最小权限原则，不应直接将整个目录设置为 `777`。

## 16. 第十二步：检查磁盘和 Docker 存储

查看磁盘空间：

```bash
df -hT
```

查看 inode：

```bash
df -i
```

查看 Docker 占用：

```bash
docker system df -v
```

磁盘或 inode 耗尽时，容器可能无法：

- 写入应用日志。
- 写入数据库数据。
- 创建临时文件。
- 更新容器可写层。
- 拉取和解压镜像。
- 保存 PID 或状态文件。

不要在未确认资源用途时直接执行带数据卷的全量清理命令。

## 17. 第十三步：检查宿主机和 Docker 服务

查看 Docker 服务状态：

```bash
systemctl status docker
```

查看 Docker 服务日志：

```bash
journalctl -u docker -n 200
```

查看宿主机重启记录：

```bash
last reboot
```

查看系统日志：

```bash
journalctl -b -1
```

如果多个容器在相同时间重启，应优先检查：

- 宿主机是否重启。
- Docker 守护进程是否重启。
- 系统是否发生 OOM。
- 磁盘或文件系统是否异常。
- 运维脚本是否执行批量重启。
- 发布平台是否重新部署服务。

## 18. 临时处理措施

容器频繁重启已经影响业务时，可以采取：

1. 保存日志、退出码和 Docker 事件。
2. 将故障实例从负载均衡中摘除。
3. 暂停异常定时任务。
4. 恢复数据库、Redis 等依赖服务。
5. 修复错误环境变量和配置。
6. 修复数据卷权限。
7. 增加合理的容器内存限制。
8. 临时关闭自动重启，保留失败现场。
9. 降低启动阶段的任务并发度。
10. 使用上一个稳定镜像版本回滚。
11. 修复健康检查后重新创建容器。
12. 将流量切换到健康实例。

临时关闭重启策略：

```bash
docker update --restart=no <容器名称或ID>
```

关闭后应继续排查，不能让核心服务长期处于停止状态。

## 19. 永久解决方案

### 19.1 修复应用退出原因

根据日志修复配置、代码异常、依赖连接和程序崩溃问题。

### 19.2 设置合理资源限制

为容器配置合理的内存和 CPU，同时为 Java 堆外内存、线程栈和系统开销预留空间。

### 19.3 增加依赖重试

应用启动时对数据库、Redis 和配置中心使用有限次数重试、指数退避和启动超时，避免依赖短暂未就绪时立即退出。

### 19.4 优化健康检查

设置合理的：

- `interval`。
- `timeout`。
- `retries`。
- `start_period`。

健康检查命令应确保镜像中存在相关工具。

### 19.5 保证主进程前台运行

启动脚本应使用 `exec` 启动应用，并正确处理 `SIGTERM`，实现优雅停止。

### 19.6 完善发布验证

发布后自动检查：

- 容器运行状态。
- 重启次数。
- 健康状态。
- 应用日志。
- 端口监听。
- 真实业务接口。
- 数据库和下游连接。

## 20. 不建议直接执行的操作

### 20.1 不建议只执行 docker restart

如果程序配置或代码存在问题，重启后仍会再次退出。

### 20.2 不建议无限自动重启

无限重启可能重复执行数据库迁移、任务消费和初始化逻辑，增加依赖服务压力。

### 20.3 不建议立即删除容器

删除后可能失去容器日志、退出状态和配置信息。应先执行 `docker inspect` 和 `docker logs`。

### 20.4 不建议直接关闭健康检查

应先确认健康检查是否合理，以及是否由外部系统根据健康状态执行重启。

### 20.5 不建议只增加内存限制

如果应用存在内存泄漏，增加内存只能延迟下一次 OOM。

## 21. 监控与预防建议

建议持续监控：

- 容器运行状态。
- 容器重启次数。
- 容器退出码。
- OOMKilled 状态。
- 健康检查状态。
- 容器 CPU 和内存。
- 容器日志错误数量。
- 宿主机内存和磁盘。
- Docker 服务状态。
- 应用启动耗时。
- 依赖服务可用性。
- 业务接口成功率。

推荐告警条件包括：

- 容器短时间内重启多次。
- `RestartCount` 持续增加。
- 出现退出码 `137` 或 `139`。
- 容器状态变为 `unhealthy`。
- 容器内存接近限制。
- 多个容器同时重启。
- 应用反复输出启动日志。
- 容器启动后短时间内退出。

## 22. 推荐排查流程

Docker 容器频繁重启时，可以按照以下顺序排查：

1. 使用 `docker ps -a` 查看容器状态。
2. 查看 `RestartCount` 和重启策略。
3. 使用 `docker logs` 查看每次退出前的日志。
4. 使用 `docker inspect` 查看退出码和错误信息。
5. 检查 `OOMKilled` 和容器内存限制。
6. 使用 `docker events` 还原重启过程。
7. 检查启动命令和主进程运行方式。
8. 检查环境变量和应用配置。
9. 检查数据库、Redis 等依赖服务。
10. 检查健康检查及外部重启机制。
11. 检查数据卷、运行用户和权限。
12. 检查磁盘空间和 inode。
13. 检查 Docker 服务和宿主机重启记录。
14. 保存现场后暂停自动重启。
15. 修复根本原因并重新创建容器。
16. 验证日志、端口、健康状态和业务接口。
17. 增加重启次数和退出码监控。

## 24. 排查结论模板

### 故障现象

Java 应用容器每隔数分钟重启一次，业务接口间歇性不可用，容器 `RestartCount` 持续增加。

### 故障确认

通过 `docker inspect` 发现容器退出码为 `137`，且 `OOMKilled=true`。容器内存限制为 2GB，而 Java 最大堆内存配置为 `-Xmx2g`。

### 根本原因

Java 堆已经占用容器的大部分内存，没有为元空间、直接内存、线程栈和 JVM 本地内存预留空间。容器总内存超过限制后被 Cgroup 强制终止，随后 Docker 的 `always` 重启策略再次启动容器。

### 临时处理

在保存日志和容器状态后，适当提高容器内存限制并滚动重新创建容器，暂时恢复服务。

### 永久修复

根据容器总内存重新设置 Java 堆大小，为堆外内存和线程栈预留安全空间；分析 Heap Dump 和 GC 日志排除内存泄漏；增加容器内存和 OOMKilled 告警。

### 验证结果

重新配置后持续观察容器内存、Java 堆和重启次数，容器内存保持在限制以内，`RestartCount` 不再增加，业务接口保持稳定。

## 25. 总结

Docker 容器频繁重启的本质通常是容器主进程不断退出，而重启策略或外部系统持续将其重新拉起。

排查时应优先查看容器日志、退出码、`OOMKilled`、重启次数和 Docker 事件。退出码能够提供初步方向，但必须结合应用日志和宿主机状态判断。退出码 `137` 可能与 OOM 有关，退出码 `139` 通常与程序崩溃有关，退出码 `0` 则可能说明主进程正常执行结束。

重启策略只能提高服务在偶发故障下的恢复能力，不能修复持续存在的配置、代码、资源或依赖问题。处理完成后，应确认容器不再重启、健康检查通过、端口正常监听，并通过真实业务请求验证服务已经稳定恢复。
