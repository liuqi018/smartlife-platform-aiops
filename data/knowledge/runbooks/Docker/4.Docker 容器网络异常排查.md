# Docker 容器网络异常排查

## 1. 问题概述

Docker 容器网络异常是指容器无法访问外部网络、宿主机或其他容器，或者外部客户端无法通过端口映射访问容器中的服务。

Docker 网络涉及容器网络命名空间、虚拟网卡、网桥、路由、DNS、iptables、端口映射和宿主机防火墙等多个环节。任何一个环节出现异常，都可能导致网络连接失败。

常见问题包括：

1. 容器无法访问互联网。
2. 容器无法解析域名。
3. 同一宿主机上的容器无法互相访问。
4. 容器无法访问宿主机服务。
5. 宿主机无法访问容器服务。
6. 外部客户端无法访问容器映射端口。
7. 容器之间偶发连接超时。
8. Docker Compose 服务名无法解析。
9. 容器网络与宿主机或公司内网网段冲突。
10. Docker iptables 或防火墙规则异常。
11. 容器服务只监听 `127.0.0.1`。
12. Docker 网络插件或守护进程异常。

排查时应先明确请求的发起方、目标地址、端口和协议，再按照容器内部、Docker 网络、宿主机和外部链路的顺序逐层定位。

## 2. 常见问题现象

Docker 容器网络异常时，通常会出现以下现象：

1. 容器内执行 `curl` 返回连接超时。
2. 容器内出现 `Connection refused`。
3. 容器内出现 `No route to host`。
4. 容器内域名解析失败。
5. 宿主机端口已经映射，但外部无法访问。
6. 同一 Compose 项目的服务无法通过服务名访问。
7. 应用无法连接 MySQL、Redis 或消息队列。
8. 容器重启后 IP 变化，固定 IP 配置失效。
9. 容器可以访问 IP，但不能访问域名。
10. 容器可以访问外部网络，但其他容器无法访问它。
11. 外部访问出现连接重置或请求超时。
12. Docker 重启后网络暂时恢复。

常见错误如下：

```text
Connection refused
```

```text
Connection timed out
```

```text
No route to host
```

```text
Network is unreachable
```

```text
Temporary failure in name resolution
```

```text
Name or service not known
```

不同错误代表的方向不同。例如，`Connection refused` 通常表示目标主机可达，但端口没有监听或被主动拒绝；`Connection timed out` 则更可能与防火墙、路由或目标服务无响应有关。

## 3. Docker 常见网络模式

### 3.1 bridge

`bridge` 是常见的默认网络模式。容器通过 Docker 网桥和 NAT 访问外部网络。

用户自定义 Bridge 网络支持容器通过名称进行 DNS 解析，通常比默认 Bridge 网络更适合多容器应用。

### 3.2 host

`host` 模式下，容器直接使用宿主机网络命名空间，不再拥有独立的容器 IP。

此模式下通常不需要端口映射，但也失去了部分网络隔离能力。

### 3.3 none

`none` 模式下，容器通常只有回环接口，不能正常访问外部网络。

### 3.4 container

容器与另一个容器共享网络命名空间。

### 3.5 overlay

Overlay 网络主要用于跨宿主机容器通信，常见于 Docker Swarm 等环境。排查时还需要检查节点间网络和相关端口。

## 4. 常见产生原因

### 4.1 服务监听地址错误

应用只监听：

```text
127.0.0.1
```

此时服务只能在容器内部通过回环地址访问，其他容器和宿主机无法访问。

需要对外提供服务时，通常应监听：

```text
0.0.0.0
```

具体监听范围还应结合安全要求设置。

### 4.2 端口映射错误

常见问题包括：

- 宿主机端口和容器端口写反。
- 映射了错误的容器端口。
- 宿主机端口被其他进程占用。
- Compose 文件修改后没有重新创建容器。
- 只绑定了宿主机的 `127.0.0.1`。

### 4.3 容器不在同一个网络

两个容器只有加入同一个用户自定义网络后，才能方便地通过容器名或服务名相互访问。

### 4.4 使用错误地址

容器中的：

```text
127.0.0.1
```

表示容器自身，而不是宿主机，也不是其他容器。

访问其他容器时，应使用 Docker Compose 服务名、容器名或正确的网络地址。

### 4.5 DNS 配置异常

容器的 `/etc/resolv.conf` 配置错误、宿主机 DNS 不可用或 Docker 内置 DNS 异常，都可能导致域名解析失败。

### 4.6 防火墙或 iptables 规则异常

Docker 通常通过 iptables 或 nftables 实现 NAT、转发和端口映射。规则缺失、被清理或与 firewalld 冲突时，可能造成网络异常。

### 4.7 IP 转发未启用

容器通过宿主机转发访问外部网络时，需要相应的 IP 转发能力。

### 4.8 网络网段冲突

Docker 网络使用的子网与宿主机局域网、VPN 或公司内网网段重叠时，可能导致路由选择错误。

### 4.9 MTU 不一致

宿主机、容器网桥、VPN 或云网络 MTU 不一致时，可能出现小数据包正常、大数据包失败或连接不稳定。

## 5. 排查前的注意事项

排查时应注意：

1. 不要立即删除 Docker 网络。
2. 不要直接清空全部 iptables 规则。
3. 不要直接关闭宿主机防火墙作为长期方案。
4. 不要依赖容器动态 IP 进行长期配置。
5. 不要只通过 Ping 判断网络是否正常。
6. 应记录源容器、目标地址、端口和协议。
7. 应分别测试容器内、宿主机和外部客户端。
8. 修改网络配置前应保存容器和网络信息。
9. 删除网络前应确认关联容器。
10. 生产环境重启 Docker 会影响多个容器，应谨慎操作。

建议先保存：

```bash
docker ps
docker network ls
docker network inspect <网络名称>
docker inspect <容器名称或ID>
ip addr
ip route
iptables-save
```

## 6. 第一步：确认容器状态

执行：

```bash
docker ps -a
```

查看容器日志：

```bash
docker logs --tail 200 <容器名称或ID>
```

如果容器没有正常运行，网络访问失败可能只是容器主进程已经退出。

查看容器健康状态：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .State.Health}}'
```

## 7. 第二步：查看容器网络配置

查看容器完整网络配置：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .NetworkSettings.Networks}}'
```

查看容器 IP：

```bash
docker inspect <容器名称或ID> \
  --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
```

重点检查：

- 容器加入了哪些网络。
- 容器 IP 是否正常分配。
- 网关是否存在。
- 网络别名是否正确。
- 两个容器是否在同一网络。
- 网络模式是否符合预期。

## 8. 第三步：进入容器检查网络

进入容器：

```bash
docker exec -it <容器名称或ID> sh
```

查看 IP：

```bash
ip addr
```

查看路由：

```bash
ip route
```

查看 DNS：

```bash
cat /etc/resolv.conf
```

部分精简镜像可能没有 `ip`、`ping`、`curl` 和 `nslookup`。不要为了排查直接修改生产镜像，可以启动临时调试容器加入相同网络。

## 9. 第四步：使用临时容器测试

启动临时 BusyBox 容器：

```bash
docker run --rm -it \
  --network <网络名称> \
  busybox sh
```

测试域名解析：

```bash
nslookup <服务名称>
```

测试目标端口：

```bash
nc -vz <目标服务名称> <端口>
```

使用带 Curl 的临时容器：

```bash
docker run --rm \
  --network <网络名称> \
  curlimages/curl \
  -v http://<服务名称>:<端口>/
```

临时容器可以避免修改原业务容器，同时验证相同 Docker 网络中的 DNS 和连接情况。

## 10. 第五步：检查服务监听地址

在容器内执行：

```bash
ss -lntp
```

如果镜像没有 `ss`，可以从宿主机查看容器进程或使用应用日志确认监听地址。

重点区分：

```text
127.0.0.1:8080
```

表示只能在容器内部访问。

```text
0.0.0.0:8080
```

表示监听容器所有 IPv4 接口。

如果应用只监听 `127.0.0.1`，即使 Docker 已正确映射端口，宿主机和外部客户端也可能无法访问。

## 11. 第六步：检查端口映射

查看端口映射：

```bash
docker port <容器名称或ID>
```

查看容器配置：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .NetworkSettings.Ports}}'
```

查看宿主机监听：

```bash
ss -lntp
```

Docker Compose 端口配置示例：

```yaml
services:
  app:
    ports:
      - "8080:8000"
```

其中：

```text
8080：宿主机端口
8000：容器端口
```

访问地址应为：

```text
宿主机IP:8080
```

而容器中的应用需要监听：

```text
0.0.0.0:8000
```

## 12. 第七步：测试分层连通性

建议按照以下顺序测试：

### 12.1 容器内部访问自身服务

```bash
curl -v http://127.0.0.1:<容器端口>/
```

### 12.2 同一网络中的其他容器访问

```bash
curl -v http://<服务名称>:<容器端口>/
```

### 12.3 宿主机访问映射端口

```bash
curl -v http://127.0.0.1:<宿主机端口>/
```

### 12.4 外部客户端访问宿主机

```bash
curl -v http://<宿主机IP>:<宿主机端口>/
```

通过分层测试可以快速定位：

- 容器内都无法访问：应用监听或服务本身有问题。
- 容器内正常、其他容器失败：Docker 网络或监听地址问题。
- 宿主机正常、外部失败：宿主机防火墙、安全组或外部路由问题。
- 所有 TCP 连接正常但业务失败：应用协议、认证或业务逻辑问题。

## 13. 第八步：检查 Docker 网络

查看网络列表：

```bash
docker network ls
```

查看网络详情：

```bash
docker network inspect <网络名称>
```

重点检查：

- Driver。
- Subnet。
- Gateway。
- 已连接容器。
- 容器网络别名。
- 网络是否为 Internal。
- 网络配置是否与其他网段冲突。

将运行中的容器连接到网络：

```bash
docker network connect <网络名称> <容器名称>
```

断开网络：

```bash
docker network disconnect <网络名称> <容器名称>
```

生产环境执行前应确认对现有连接和应用的影响。

## 14. 第九步：检查 DNS

查看容器 DNS：

```bash
docker exec <容器名称或ID> \
  cat /etc/resolv.conf
```

测试服务名：

```bash
docker exec <容器名称或ID> \
  getent hosts <服务名称>
```

Docker 用户自定义网络通常支持通过容器名或网络别名解析。

常见 DNS 问题包括：

- 容器不在同一网络。
- 服务名拼写错误。
- 手动设置了不可用 DNS。
- 宿主机 DNS 异常。
- VPN 修改了宿主机 DNS。
- 应用长期缓存了旧 IP。
- 使用默认 Bridge 网络并错误依赖容器名解析。

不要将容器动态 IP 写死在应用配置中。容器重建后 IP 可能变化，应使用服务名或稳定的服务发现机制。

## 15. 第十步：检查宿主机路由和转发

查看宿主机路由：

```bash
ip route
```

查看 Docker 网桥：

```bash
ip addr show docker0
```

查看 IP 转发：

```bash
sysctl net.ipv4.ip_forward
```

正常需要转发的环境中，通常应为：

```text
net.ipv4.ip_forward = 1
```

如果 Docker 网络子网与内网或 VPN 网段重叠，宿主机可能将数据包发送到错误的网卡。

查看目标路由：

```bash
ip route get <目标IP>
```

发现网段冲突后，应规划新的 Docker 子网，并在业务维护窗口重新创建网络和容器。

## 16. 第十一步：检查 iptables 和防火墙

查看 iptables：

```bash
iptables -L -n -v
```

查看 NAT 规则：

```bash
iptables -t nat -L -n -v
```

查看 Docker 相关链：

```bash
iptables -L DOCKER -n -v
iptables -L DOCKER-USER -n -v
```

查看完整规则：

```bash
iptables-save
```

如果使用 nftables：

```bash
nft list ruleset
```

如果使用 firewalld：

```bash
firewall-cmd --list-all
```

重点检查：

- FORWARD 链策略。
- DOCKER 链是否存在。
- DOCKER-USER 链是否丢弃流量。
- NAT 端口映射是否生成。
- firewalld 是否覆盖或刷新规则。
- 云安全组是否放行宿主机端口。

不应直接执行清空全部 iptables 规则的操作，否则可能导致其他容器网络和系统安全策略失效。

## 17. 第十二步：检查网络带宽、丢包和 MTU

查看网卡统计：

```bash
ip -s link
```

查看 Docker 网桥统计：

```bash
ip -s link show docker0
```

测试不分片数据包：

```bash
ping -M do -s 1472 -c 4 <目标IP>
```

如果小请求正常、大请求失败，应检查：

- 宿主机网卡 MTU。
- Docker 网络 MTU。
- VPN 或隧道 MTU。
- 云网络 MTU。
- 中间防火墙是否阻止必要的 ICMP 报文。

查看容器网卡 MTU：

```bash
docker exec <容器名称或ID> ip link
```

MTU 调整会影响网络和现有容器，不应在没有确认链路要求时随意修改。

## 18. 第十三步：使用 tcpdump 抓包

在宿主机抓取指定端口：

```bash
tcpdump -i any port <端口>
```

抓取指定容器 IP：

```bash
tcpdump -i any host <容器IP>
```

保存抓包：

```bash
tcpdump -i any \
  host <容器IP> and port <端口> \
  -c 1000 \
  -w /tmp/docker-network.pcap
```

通过抓包可以确认：

- 请求是否到达宿主机。
- 请求是否转发到容器。
- 容器是否返回响应。
- 是否存在 TCP 重传。
- 哪一方发送 RST。
- 响应是否在 NAT 或防火墙环节丢失。
- DNS 请求是否获得响应。

生产环境应限制抓包的主机、端口、数量和文件大小，避免产生过大文件或收集无关敏感数据。

## 19. Docker Compose 网络排查

查看最终配置：

```bash
docker compose config
```

查看容器和网络：

```bash
docker compose ps
docker network ls
```

Compose 示例：

```yaml
services:
  app:
    image: example-app
    networks:
      - backend

  mysql:
    image: mysql:8
    networks:
      - backend

networks:
  backend:
    driver: bridge
```

应用连接数据库时应使用：

```text
mysql:3306
```

而不是：

```text
127.0.0.1:3306
```

如果宿主机将 MySQL 映射为 `3307:3306`，容器之间仍然应该通过服务名访问容器端口 `3306`，而不是宿主机映射端口 `3307`。

## 20. 常见临时处理措施

容器网络异常已经影响业务时，可以采取：

1. 确认应用监听 `0.0.0.0`。
2. 修复错误的端口映射。
3. 将相关容器加入同一用户自定义网络。
4. 使用服务名代替固定容器 IP。
5. 修复容器 DNS 配置。
6. 放行必要的宿主机防火墙和安全组端口。
7. 修复 IP 转发和 Docker NAT 规则。
8. 暂停冲突的 VPN 或检查路由。
9. 在保存现场后重新创建异常网络。
10. 必要时在维护窗口重启 Docker 服务。
11. 将流量切换到健康实例。
12. 使用临时调试容器验证网络。

重启 Docker 会影响宿主机上的多个容器，应作为经过评估后的措施。

## 21. 永久解决方案

### 21.1 统一网络规划

为 Docker 网络规划不与公司内网、云网络和 VPN 冲突的独立子网。

### 21.2 使用服务名通信

同一 Docker 网络中的容器应通过服务名或网络别名通信，不依赖动态容器 IP。

### 21.3 正确配置应用监听

容器服务对其他容器或外部提供访问时，应监听正确的网络接口和端口。

### 21.4 完善端口和防火墙管理

统一管理端口映射、宿主机防火墙、云安全组和上级网络 ACL，避免配置不一致。

### 21.5 建立依赖重试和超时

容器应用应设置合理的连接超时、读取超时、有限重试和指数退避，避免短暂网络波动导致服务退出。

### 21.6 增加网络监控

监控容器连接失败率、DNS 解析、TCP 重传、网络流量和依赖服务可用性。

## 22. 不建议直接执行的操作

### 22.1 不建议直接清空 iptables

Docker 网络依赖 NAT 和转发规则，清空规则可能导致全部容器网络中断。

### 22.2 不建议关闭防火墙作为永久方案

应定位具体拦截规则，并按照最小权限原则放行必要流量。

### 22.3 不建议固定容器 IP

普通容器重建后 IP 可能变化。应优先使用 Docker DNS 和服务名。

### 22.4 不建议只通过 Ping 判断

Ping 使用 ICMP，业务访问通常使用 TCP 或 UDP。Ping 不通不代表端口一定不通，Ping 通也不代表服务正常。

### 22.5 不建议随意删除 Docker 网络

网络仍被容器使用时可能无法删除，强制重建也可能导致容器短暂中断和地址变化。

## 23. 监控与预防建议

建议持续监控：

- 容器网络接收和发送流量。
- 网络错误包和丢包。
- TCP 连接失败率。
- TCP 重传率。
- DNS 解析耗时和失败率。
- 容器端口监听状态。
- 宿主机映射端口可用性。
- 容器到依赖服务的连接耗时。
- Docker 网络数量和网段。
- 宿主机防火墙规则变化。
- Docker 服务状态。
- 外部接口成功率。

推荐告警条件包括：

- 容器 DNS 解析连续失败。
- 关键依赖端口连续不可达。
- TCP 重传率明显升高。
- 容器网络错误包持续增加。
- 端口映射探测失败。
- Docker 网桥或网络接口消失。
- 多个容器同时无法访问外部网络。
- 容器网络与新接入网段发生冲突。

## 24. 推荐排查流程

Docker 容器网络异常时，可以按照以下顺序排查：

1. 明确源容器、目标地址、端口和协议。
2. 确认源容器和目标容器正常运行。
3. 检查应用监听地址和端口。
4. 检查 Docker 端口映射。
5. 查看容器 IP、网关和网络模式。
6. 确认相关容器是否加入同一网络。
7. 在容器内检查路由和 DNS。
8. 使用临时调试容器测试解析和端口。
9. 分别测试容器内部、容器之间、宿主机和外部访问。
10. 检查 Docker 网络的子网和网关。
11. 检查是否存在网段冲突。
12. 检查 IP 转发、iptables 和 firewalld。
13. 检查云安全组和上级网络 ACL。
14. 检查丢包、MTU 和网卡错误。
15. 必要时使用 tcpdump 抓包。
16. 修复后重新验证完整访问链路。
17. 增加 DNS、端口和依赖连接监控。

## 25. 常用排查命令汇总

```bash
# 查看容器状态
docker ps -a

# 查看容器网络配置

  --format '{{json .NetworkSettings.Networks}}'

  --format '{{json .NetworkSettings.Ports}}'

# 将容器连接到网络

# 查看容器 IP 和路由
docker exec <容器名称或ID> ip addr
docker exec <容器名称或ID> ip route

# 查看容器 DNS
docker exec <容器名称或ID> cat /etc/resolv.conf

# 使用临时容器测试 DNS
docker run --rm \
  --network <网络名称> \
  busybox nslookup <服务名称>

# 使用临时容器测试端口
docker run --rm \
  --network <网络名称> \
  busybox nc -vz <服务名称> <端口>

# 查看宿主机监听端口
ss -lntp

# 查看宿主机路由
ip route

# 查看访问目标使用的路由
ip route get <目标IP>

# 查看 IP 转发
sysctl net.ipv4.ip_forward

# 查看 iptables
iptables -L -n -v
iptables -t nat -L -n -v
iptables -L DOCKER -n -v
iptables -L DOCKER-USER -n -v

# 查看 nftables
nft list ruleset

# 查看 firewalld
firewall-cmd --list-all

# 查看网卡错误
ip -s link

# 抓取指定容器数据包

  host <容器IP> and port <端口> \

  -w /tmp/docker-network.pcap

# 检查 Compose 配置
docker compose config
```

## 26. 排查结论模板

### 故障现象

应用容器可以正常启动，但无法连接同一宿主机上的 MySQL 容器，应用日志持续出现数据库连接失败。

### 故障确认

进入应用容器后测试发现 `127.0.0.1:3307` 无法连接。检查 Docker Compose 配置后确认 MySQL 服务名为 `mysql`，容器端口为 `3306`，宿主机映射端口为 `3307`。

### 根本原因

应用错误地使用 `127.0.0.1:3307` 连接数据库。容器中的 `127.0.0.1` 表示应用容器自身，而 `3307` 是提供给宿主机和外部客户端使用的映射端口。容器之间应通过 Compose 服务名和容器端口访问。

### 临时处理

将数据库地址修改为 `mysql:3306`，确认两个容器加入同一 Docker 网络后重新创建应用容器。

### 永久修复

统一通过环境变量配置服务名和容器端口，禁止在容器环境中写死 `127.0.0.1` 和动态容器 IP，并在发布流程中增加依赖服务 DNS 和端口连通性检查。

### 验证结果

重新创建容器后，应用可以通过 `mysql:3306` 正常连接数据库，健康检查通过，业务接口恢复正常。

## 27. 总结

Docker 容器网络异常排查的关键是区分容器内部地址、容器网络地址、宿主机映射端口和外部访问地址。

容器中的 `127.0.0.1` 只代表容器自身。容器之间应加入同一个用户自定义网络，并通过服务名和容器端口进行通信；外部客户端则通过宿主机 IP 和映射端口访问。

排查时应先确认应用是否监听正确地址，再逐层检查容器 IP、Docker 网络、DNS、端口映射、宿主机路由、防火墙和安全组。使用临时调试容器可以在不修改业务镜像的情况下验证 DNS 和端口连通性。

如果基础配置正常但连接仍然异常，可以通过 `tcpdump` 判断数据包是否到达宿主机、是否转发到容器以及响应在哪个环节丢失。修复后应从容器内部、其他容器、宿主机和外部客户端分别验证完整访问链路。
