# Docker 容器启动失败排查

## 1. 问题概述

Docker 容器启动失败是指容器无法正常创建或启动，或者启动后立即退出、反复重启，无法稳定提供服务。

容器启动涉及镜像、启动命令、环境变量、端口映射、数据卷、网络、资源限制和宿主机 Docker 服务等多个环节。任何一个环节配置错误，都可能导致容器无法正常运行。

常见问题包括：

1. 镜像不存在或拉取失败。
2. 容器启动命令错误。
3. 容器主进程执行结束。
4. 应用配置或环境变量缺失。
5. 宿主机端口被占用。
6. 数据卷挂载失败。
7. 文件或目录权限不足。
8. 依赖服务不可用。
9. 容器达到内存限制。
10. Docker 网络配置异常。
11. 镜像架构与服务器不兼容。
12. Docker 守护进程异常。

排查时应先查看容器状态、退出码和日志，再根据错误信息检查启动命令、挂载、端口、资源和依赖服务。

## 2. 常见问题现象

Docker 容器启动失败时，通常会出现以下现象：

1. `docker start` 返回错误。
2. `docker compose up` 执行失败。
3. 容器状态显示 `Exited`。
4. 容器状态显示 `Restarting`。
5. 容器刚启动就立即退出。
6. 容器退出码为 `1`、`126`、`127` 或 `137`。
7. 容器日志中出现配置错误。
8. 端口没有正常监听。
9. 容器健康状态显示 `unhealthy`。
10. 容器无法连接数据库、Redis 或其他服务。
11. 数据卷中的文件无法读取或写入。
12. 宿主机内存、磁盘或 inode 不足。

常见错误如下：

```text
No such container
```

```text
Unable to find image
```

```text
pull access denied
```

```text
exec format error
```

```text
permission denied
```

```text
address already in use
```

```text
no space left on device
```

```text
executable file not found in $PATH
```

## 3. 排查前的注意事项

排查容器启动失败时，应注意：

1. 不要立即删除故障容器。
2. 删除前应保存容器日志和配置。
3. 不要直接清理全部 Docker 镜像和数据卷。
4. 不要对挂载目录直接执行 `chmod -R 777`。
5. 不要只查看应用日志，还要查看 Docker 事件和宿主机日志。
6. 不要只重启容器，应确认退出的根本原因。
7. 数据卷中可能保存数据库或业务数据，禁止随意删除。
8. 应确认操作的是正确环境和正确容器。

建议先保存：

```bash
docker ps -a
docker inspect <容器名称或ID>
docker logs --tail 200 <容器名称或ID>
docker system df
df -h
free -h
```

## 4. 第一步：查看容器状态

执行：

```bash
docker ps -a
```

重点关注：

- 容器名称。
- 使用的镜像。
- 创建时间。
- 当前状态。
- 退出时间。
- 端口映射。
- 是否反复重启。

只查看指定容器：

```bash
docker ps -a --filter name=<容器名称>
```

如果容器显示：

```text
Exited (1)
```

表示容器主进程返回退出码 1。

如果显示：

```text
Restarting
```

说明容器配置了重启策略，但主进程反复退出。

## 5. 第二步：查看容器日志

执行：

```bash
docker logs --tail 200 <容器名称或ID>
```

实时查看：

```bash
docker logs -f <容器名称或ID>
```

查看带时间戳的日志：

```bash
docker logs --timestamps --tail 200 <容器名称或ID>
```

重点查找：

```text
error
failed
fatal
exception
denied
timeout
not found
address already in use
```

如果没有任何日志，可能说明：

- 容器主进程还未执行就失败。
- 启动命令不存在。
- 文件没有执行权限。
- 镜像架构不兼容。
- 日志被写入容器内部文件。
- 应用在初始化日志之前退出。

## 6. 第三步：查看退出码和错误信息

查看退出码：

```bash
docker inspect <容器名称或ID> --format '{{.State.ExitCode}}'
```

查看错误信息：

```bash
docker inspect <容器名称或ID> --format '{{.State.Error}}'
```

查看是否发生 OOM：

```bash
docker inspect <容器名称或ID> --format '{{.State.OOMKilled}}'
```

常见退出码：

| 退出码 | 常见含义                         |
| ------ | -------------------------------- |
| `0`    | 主进程正常执行结束               |
| `1`    | 应用程序一般性错误               |
| `126`  | 命令存在但无法执行               |
| `127`  | 启动命令不存在                   |
| `137`  | 进程收到 `SIGKILL`，可能发生 OOM |
| `139`  | 进程发生段错误                   |
| `143`  | 进程收到 `SIGTERM`               |

退出码 `137` 不一定百分之百表示 OOM，应结合 `OOMKilled` 和宿主机内核日志确认。

## 7. 第四步：检查镜像

查看本地镜像：

```bash
docker images
```

拉取镜像：

```bash
docker pull <镜像名称>:<标签>
```

查看镜像详细信息：

```bash
docker image inspect <镜像名称>:<标签>
```

镜像拉取失败的常见原因包括：

- 镜像名称或标签错误。
- 镜像不存在。
- 私有仓库认证失败。
- 网络无法访问镜像仓库。
- 镜像仓库证书异常。
- 磁盘空间不足。
- 镜像架构与服务器不兼容。

查看服务器架构：

```bash
uname -m
```

查看镜像架构：

```bash
docker image inspect <镜像名称>:<标签> --format '{{.Architecture}}'
```

如果 ARM 镜像运行在 x86 服务器上，或者相反，可能出现：

```text
exec format error
```

## 8. 第五步：检查启动命令

查看容器启动命令：

```bash
docker inspect <容器名称或ID> --format '{{json .Config.Entrypoint}} {{json .Config.Cmd}}'
```

常见问题包括：

- `ENTRYPOINT` 路径错误。
- `CMD` 参数错误。
- 程序不在 `$PATH` 中。
- Shell 脚本没有执行权限。
- 脚本解释器不存在。
- 脚本使用 Windows CRLF 换行符。
- 启动脚本执行结束后没有前台进程。
- Docker Compose 的 `command` 覆盖了镜像默认命令。

容器必须保持一个前台主进程。如果启动脚本将程序放入后台后自身退出，容器也会退出。

## 9. 第六步：检查环境变量

查看容器环境变量：

```bash
docker inspect <容器名称或ID> --format '{{json .Config.Env}}'
```

Docker Compose 可以检查最终配置：

```bash
docker compose config
```

常见问题包括：

- 数据库地址错误。
- Redis 地址错误。
- 密码或 Token 缺失。
- 环境变量名称拼写错误。
- `.env` 文件没有被加载。
- 环境变量中存在错误引号或特殊字符。
- 容器中使用了 `127.0.0.1` 访问其他容器。
- 生产和测试配置混用。

不要在排查输出中直接暴露密码、Token 和私钥。

## 10. 第七步：检查端口冲突

查看宿主机端口：

```bash
ss -lntp
```

查看指定端口：

```bash
ss -lntp | grep ':8080'
```

查看容器端口映射：

```bash
docker port <容器名称或ID>
```

常见错误：

```text
Bind for 0.0.0.0:8080 failed: port is already allocated
```

处理方式包括：

- 停止确认无用的占用进程。
- 修改宿主机映射端口。
- 避免重复启动相同服务。
- 检查 Docker Compose 是否重复声明端口。

容器内部端口可以相同，但同一宿主机 IP 上的映射端口不能冲突。

## 11. 第八步：检查数据卷挂载

查看挂载信息：

```bash
docker inspect <容器名称或ID> --format '{{json .Mounts}}'
```

检查宿主机目录：

```bash
ls -ld /宿主机/挂载目录
```

常见问题包括：

- 宿主机路径不存在。
- 挂载了错误目录。
- 文件被目录覆盖。
- 目录被文件覆盖。
- 容器用户没有读写权限。
- SELinux 阻止访问。
- Docker Compose 使用了错误的相对路径。
- 挂载后的配置文件格式错误。

使用相对路径时，应确认 Docker Compose 的项目目录和实际解析结果。

## 12. 第九步：检查权限和 SELinux

查看宿主机目录权限：

```bash
ls -ld /宿主机/挂载目录
```

查看容器运行用户：

```bash
docker inspect <容器名称或ID> --format '{{.Config.User}}'
```

检查 SELinux：

```bash
getenforce
```

查看拒绝日志：

```bash
ausearch -m AVC -ts recent
```

如果问题与 SELinux 有关，应根据实际用途调整文件上下文或使用合适的挂载标签，不建议直接永久关闭 SELinux。

也不建议通过以下方式粗暴解决：

```bash
chmod -R 777 /宿主机/挂载目录
```

应根据容器运行用户设置正确的 UID、GID 和最小必要权限。

## 13. 第十步：检查依赖服务

容器应用可能依赖：

- MySQL。
- Redis。
- Kafka。
- RabbitMQ。
- Elasticsearch。
- 配置中心。
- 注册中心。
- 外部 HTTP API。

查看容器网络：

```bash
docker network ls
```

查看网络详情：

```bash
docker network inspect <网络名称>
```

临时启动调试容器测试：

```bash
docker run --rm --network <网络名称> busybox nslookup <服务名称>
```

检查端口：

```bash
docker run --rm --network <网络名称> busybox nc -vz <服务名称> <端口>
```

容器中的 `127.0.0.1` 指向容器自身。如果需要访问其他容器，应使用容器名称、Compose 服务名或对应网络地址。

## 14. 第十一步：检查内存和 OOM

查看容器资源使用：

```bash
docker stats
```

查看内存限制：

```bash
docker inspect <容器名称或ID> --format '{{.HostConfig.Memory}}'
```

检查 OOM：

```bash
docker inspect <容器名称或ID> --format '{{.State.OOMKilled}}'
```

查看宿主机内核日志：

```bash
dmesg -T | grep -iE 'out of memory|oom|killed process'
```

常见问题包括：

- 容器内存限制过小。
- Java `-Xmx` 接近容器内存上限。
- 应用启动时一次性加载大量数据。
- 内存泄漏。
- 宿主机整体内存不足。

Java 容器除了堆内存，还需要为元空间、直接内存、线程栈和 JVM 本地内存预留空间。

## 15. 第十二步：检查磁盘空间

查看宿主机磁盘：

```bash
df -hT
```

查看 inode：

```bash
df -i
```

查看 Docker 空间：

```bash
docker system df
```

查看详细占用：

```bash
docker system df -v
```

磁盘或 inode 耗尽时，容器可能无法：

- 创建可写层。
- 写入日志。
- 创建临时文件。
- 解压镜像。
- 写入数据库数据。
- 创建容器运行目录。

不要在未确认用途时直接执行：

```bash
docker system prune -a --volumes
```

该命令可能删除仍然重要的镜像、缓存和数据卷。

## 16. 第十三步：检查 Docker 服务

查看 Docker 服务状态：

```bash
systemctl status docker
```

查看 Docker 服务日志：

```bash
journalctl -u docker -n 200
```

查看 Docker 信息：

```bash
docker info
```

如果所有容器都无法启动，应重点检查：

- Docker 守护进程状态。
- Docker 数据目录。
- 存储驱动。
- 磁盘空间。
- iptables 或 nftables。
- Cgroup 配置。
- Docker 服务日志。
- 宿主机内核错误。

## 17. Docker Compose 排查

检查最终配置：

```bash
docker compose config
```

启动并查看前台日志：

```bash
docker compose up
```

查看服务状态：

```bash
docker compose ps -a
```

查看服务日志：

```bash
docker compose logs --tail 200 <服务名称>
```

常见问题包括：

- YAML 缩进错误。
- `.env` 文件格式错误。
- 服务名称写错。
- 端口重复。
- 数据卷路径错误。
- 环境变量未定义。
- 依赖服务没有正常启动。
- 健康检查失败。
- Compose 文件版本和字段使用不当。

## 18. 常见临时处理措施

容器启动失败时，可以采取：

1. 保存容器日志和 `inspect` 结果。
2. 修复错误的环境变量。
3. 修复启动命令和脚本权限。
4. 修改冲突的宿主机端口。
5. 修复数据卷目录权限。
6. 恢复数据库或 Redis 等依赖。
7. 增加合理的容器内存限制。
8. 清理确认无用的镜像和构建缓存。
9. 修复 Docker 网络配置。
10. 使用正确架构的镜像重新创建容器。

修改容器配置后，通常需要重新创建容器，而不是只执行 `docker restart`。

## 19. 推荐排查流程

Docker 容器启动失败时，可以按照以下顺序排查：

1. 使用 `docker ps -a` 查看容器状态。
2. 使用 `docker logs` 查看应用日志。
3. 使用 `docker inspect` 查看退出码和错误信息。
4. 检查是否发生 OOM。
5. 检查镜像名称、标签和架构。
6. 检查 `ENTRYPOINT` 和 `CMD`。
7. 检查环境变量和 Compose 最终配置。
8. 检查宿主机端口冲突。
9. 检查数据卷路径和权限。
10. 检查 SELinux 拒绝日志。
11. 检查容器网络和依赖服务。
12. 检查宿主机内存、磁盘和 inode。
13. 检查 Docker 守护进程状态和日志。
14. 修复后重新创建容器。
15. 验证进程、日志、端口和健康状态。

## 21. 排查结论模板

### 故障现象

应用容器启动后立即退出，`docker ps -a` 显示退出码为 1，服务端口没有监听。

### 故障确认

通过 `docker logs` 发现应用无法读取挂载的配置文件。检查 `docker inspect` 后确认宿主机配置目录已经挂载，但容器运行用户没有读取权限。

### 根本原因

发布脚本重新创建配置目录后，目录所有者变为 root，容器使用普通用户运行，因此应用初始化阶段无法读取配置并直接退出。

### 临时处理

将配置目录的所有者和权限调整为容器运行用户可以读取的范围，然后重新创建容器。

### 永久修复

修改发布脚本，在创建配置目录后统一设置正确的 UID、GID 和最小必要权限，并在发布前增加挂载文件和权限检查。

### 验证结果

重新创建容器后，容器状态持续为 `Up`，应用日志无新增错误，目标端口正常监听，健康检查通过。

## 22. 总结

Docker 容器启动失败排查的关键是先查看容器状态、退出码和日志，再沿着镜像、启动命令、环境变量、端口、挂载、权限、网络和资源限制逐步排查。

如果容器启动后立即退出，通常说明主进程执行结束或发生异常；如果容器反复重启，应检查重启策略和主进程退出原因；如果退出码为 137，应结合 `OOMKilled` 和内核日志确认是否发生内存不足。

重启容器只能重新执行原有配置，无法修复错误的命令、挂载和环境变量。处理完成后，应验证容器持续运行、日志正常、端口已经监听，并通过真实接口或健康检查确认服务恢复。
