# Docker 磁盘空间不足排查

## 1. 问题概述

Docker 磁盘空间不足是指 Docker 镜像、容器可写层、数据卷、容器日志或构建缓存持续占用宿主机磁盘，导致 Docker 数据目录所在文件系统空间不足。

Docker 默认数据目录通常为：

```text
/var/lib/docker
```

如果该目录位于根分区，Docker 数据不断增长时可能直接占满系统根分区，进而影响 Docker、操作系统和其他服务。

磁盘空间不足后，常见影响包括：

1. 无法拉取或解压镜像。
2. 无法创建新容器。
3. 容器无法启动。
4. 容器无法写入日志。
5. 数据库容器无法写入数据。
6. Docker 构建镜像失败。
7. 应用出现 `No space left on device`。
8. Docker 守护进程异常。
9. 宿主机系统服务无法写入日志。
10. 已运行容器发生异常退出。

Docker 磁盘空间不足排查的核心目标包括：

1. 确认空间不足的文件系统。
2. 确认 Docker 数据目录位置。
3. 区分镜像、容器、日志、数据卷和构建缓存占用。
4. 定位持续增长的具体资源。
5. 在不删除业务数据的前提下安全释放空间。
6. 配置日志轮转、镜像清理和容量监控。
7. 必要时扩容或迁移 Docker 数据目录。

## 2. 常见问题现象

Docker 磁盘空间不足时，通常会出现以下现象：

1. `docker pull` 执行失败。
2. `docker build` 执行失败。
3. 容器无法创建或启动。
4. 容器日志停止写入。
5. 数据库容器出现写入错误。
6. Docker Compose 启动失败。
7. 宿主机根分区使用率达到 100%。
8. Docker 命令执行缓慢或报错。
9. 容器可写层持续增长。
10. `/var/lib/docker` 占用大量空间。
11. 删除容器后空间没有明显释放。
12. `df` 显示磁盘已满，但 `du` 统计结果偏小。
13. 磁盘仍有容量，但 inode 已经耗尽。
14. Docker 服务无法正常启动。

常见错误如下：

```text
No space left on device
```

```text
write /var/lib/docker/...: no space left on device
```

```text
failed to register layer
```

```text
failed to copy files
```

```text
failed to create shim task
```

```text
input/output error
```

其中，`No space left on device` 既可能表示磁盘容量耗尽，也可能表示 inode 耗尽，需要分别检查。

## 3. Docker 磁盘占用的主要来源

### 3.1 Docker 镜像

每次发布和构建可能产生新的镜像版本。旧镜像如果没有清理，会持续占用磁盘。

常见情况包括：

- 保留大量历史版本镜像。
- 存在无标签悬空镜像。
- 基础镜像重复。
- CI/CD 频繁构建镜像。
- 拉取过多个测试镜像。
- 镜像本身层数和体积过大。

### 3.2 容器可写层

容器运行后对镜像文件系统的修改会写入容器可写层。

常见增长来源包括：

- 应用日志写入容器内部。
- 上传文件保存在容器内部。
- 临时文件没有清理。
- 缓存写入容器可写层。
- 数据库数据没有挂载数据卷。
- 应用生成报表、图片和压缩包。

### 3.3 容器日志

Docker 使用 `json-file` 日志驱动时，容器标准输出和标准错误通常会写入宿主机文件。

常见路径如下：

```text
/var/lib/docker/containers/<容器ID>/<容器ID>-json.log
```

如果没有配置日志轮转，单个容器日志可能增长到几十 GB。

### 3.4 Docker 数据卷

数据卷可能保存：

- MySQL 数据。
- Redis 持久化文件。
- Elasticsearch 索引。
- 上传文件。
- 应用数据。
- 历史备份。
- 已删除容器遗留的数据。

数据卷通常包含重要业务数据，不能因为显示为未使用就直接删除。

### 3.5 构建缓存

频繁执行 `docker build` 或 BuildKit 构建时，会生成构建缓存和中间层。

### 3.6 已停止容器

已停止容器仍然保留容器元数据和可写层。长期不清理可能持续占用空间。

### 3.7 临时文件和异常残留

Docker 构建中断、镜像拉取失败、容器异常退出或存储驱动异常，可能遗留临时数据。

## 4. 排查前的注意事项

排查时应注意：

1. 不要直接删除 `/var/lib/docker`。
2. 不要直接清理所有 Docker 数据卷。
3. 不要在未确认用途时执行全量 Prune。
4. 数据库容器的数据卷可能包含唯一业务数据。
5. 删除镜像前应确认是否用于回滚。
6. 删除停止容器前应确认是否需要保留现场。
7. 清理日志前应确认日志保留要求。
8. 应先记录磁盘状态和 Docker 资源信息。
9. 应同时检查磁盘容量和 inode。
10. 在磁盘完全耗尽时，应优先停止持续写入的非核心任务。

建议先保存：

```bash
df -hT
df -i
docker info
docker system df -v
docker ps -a --size
docker volume ls
docker images
```

## 5. 第一步：查看文件系统空间

执行：

```bash
df -hT
```

重点关注：

- Docker 数据目录所在文件系统。
- `Used`。
- `Avail`。
- `Use%`。
- 文件系统类型。
- 挂载点。

如果 `/var/lib/docker` 没有单独挂载数据盘，通常会占用根分区空间。

查看 Docker 数据目录：

```bash
docker info --format '{{.DockerRootDir}}'
```

也可以执行：

```bash
docker info | grep 'Docker Root Dir'
```

## 6. 第二步：检查 inode

执行：

```bash
df -i
```

如果磁盘容量还有剩余，但 inode 使用率达到 100%，Docker 同样无法创建新文件。

inode 耗尽常见原因包括：

- 容器产生大量小文件。
- OverlayFS 层中存在大量文件。
- 缓存或临时文件持续增长。
- 应用按请求创建独立文件。
- 构建缓存中包含大量小文件。

需要根据 Docker 根目录或具体数据卷逐级统计文件数量，避免直接扫描整个文件系统。

## 7. 第三步：查看 Docker 整体占用

执行：

```bash
docker system df
```

查看详细占用：

```bash
docker system df -v
```

输出通常包括：

- Images。
- Containers。
- Local Volumes。
- Build Cache。
- 可回收空间。

需要注意，`RECLAIMABLE` 表示 Docker 认为可能回收的空间，不代表可以在不了解业务影响时直接删除。

共享镜像层可能被多个镜像共同使用，因此各镜像显示的虚拟大小不能直接相加作为真实磁盘占用。

## 8. 第四步：查看镜像占用

查看镜像：

```bash
docker images
```

按仓库和标签查看：

```bash
docker images --digests
```

查看悬空镜像：

```bash
docker images -f dangling=true
```

查看镜像历史：

```bash
docker history <镜像名称>:<标签>
```

镜像过大的常见原因包括：

- 使用完整操作系统作为基础镜像。
- 将构建工具和运行环境放在同一镜像。
- 没有使用多阶段构建。
- 构建上下文包含无用文件。
- 将日志、数据或依赖缓存打入镜像。
- Dockerfile 层设计不合理。

## 9. 第五步：查看容器可写层

查看容器大小：

```bash
docker ps -a --size
```

其中：

- `size` 通常表示容器可写层大小。
- `virtual size` 通常包含镜像只读层。

如果某个容器可写层持续增长，应检查：

- 日志是否写入容器内部。
- 上传文件是否保存到容器内部。
- 临时文件是否未清理。
- 数据库是否未挂载数据卷。
- 应用缓存是否写入容器文件系统。
- Core Dump 或 Heap Dump 是否生成在容器内。

容器可写层不适合长期保存业务数据。重要数据应写入明确的数据卷、绑定挂载目录或外部存储。

## 10. 第六步：查看容器日志

查看容器日志配置：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .HostConfig.LogConfig}}'
```

查看日志路径：

```bash
docker inspect <容器名称或ID> \
  --format '{{.LogPath}}'
```

查看日志文件大小：

```bash
du -h "$(docker inspect <容器名称或ID> --format '{{.LogPath}}')"
```

查找大型 JSON 日志：

```bash
find /var/lib/docker/containers \
  -name '*-json.log' \
  -type f \
  -size +500M \
  -ls 2>/dev/null
```

容器日志持续增长的常见原因包括：

- 没有配置日志轮转。
- 应用开启 Debug 日志。
- 异常堆栈重复打印。
- 请求和响应内容全部输出。
- 容器重启循环反复打印启动日志。
- 日志采集程序没有及时读取。

## 11. 第七步：配置容器日志轮转

Docker Compose 示例：

```yaml
services:
  app:
    image: example-app
    logging:
      driver: json-file
      options:
        max-size: "100m"
        max-file: "5"
```

Docker 守护进程配置示例：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "5"
  }
}
```

常见配置文件路径：

```text
/etc/docker/daemon.json
```

修改 Docker 守护进程配置后通常需要重启 Docker 服务，并且已有容器可能需要重新创建才能应用新的日志配置。

生产环境重启 Docker 前应评估对所有容器的影响。

## 12. 第八步：查看数据卷占用

查看数据卷：

```bash
docker volume ls
```

查看数据卷详情：

```bash
docker volume inspect <数据卷名称>
```

查看数据卷挂载位置：

```bash
docker volume inspect <数据卷名称> \
  --format '{{.Mountpoint}}'
```

查看空间：

```bash
du -sh <数据卷挂载位置>
```

查看容器使用的数据卷：

```bash
docker inspect <容器名称或ID> \
  --format '{{json .Mounts}}'
```

清理数据卷前必须确认：

- 是否属于数据库。
- 是否包含上传文件。
- 是否用于备份。
- 是否仍被其他容器引用。
- 是否存在可用备份。
- 删除后是否可以恢复。

## 13. 第九步：查看构建缓存

查看构建缓存：

```bash
docker builder du
```

如果使用 Buildx：

```bash
docker buildx du
```

构建缓存较大通常与以下情况有关：

- 频繁执行镜像构建。
- 多个分支生成不同缓存。
- 基础镜像频繁变化。
- 构建上下文过大。
- 没有定期清理旧缓存。
- CI 构建节点长期复用。

构建缓存通常可以重新生成，但清理后下次构建速度可能下降。

## 14. 第十步：确认实际占用目录

查看 Docker 根目录大小：

```bash
du -sh /var/lib/docker
```

查看一级目录：

```bash
du -xhd1 /var/lib/docker 2>/dev/null | sort -h
```

常见目录包括：

```text
containers
image
overlay2
volumes
buildkit
```

不要直接进入 `overlay2` 删除文件。Docker 存储层由 Docker 管理，手动删除可能破坏镜像和容器元数据。

如果 `overlay2` 占用较大，应通过 Docker 命令定位镜像、容器和构建缓存，而不是手工删除层目录。

## 15. 第十一步：排查已删除但仍被占用的文件

如果 `df` 显示磁盘已满，但 `du` 统计明显偏小，应执行：

```bash
lsof +L1
```

可能存在已经删除但仍被进程打开的 Docker 日志或容器文件。

此时目录中已经看不到文件，但空间只有在进程关闭文件描述符后才会释放。

处理方式包括：

- 让应用重新打开日志。
- 正常重启对应容器。
- 重启持有文件的进程。
- 在确认影响后处理对应文件描述符。

应优先正常重启相关容器，而不是直接操作未知文件描述符。

## 16. 安全清理镜像

清理悬空镜像：

```bash
docker image prune
```

清理未被容器使用的镜像：

```bash
docker image prune -a
```

执行 `-a` 前应确认：

- 镜像是否用于快速回滚。
- 是否属于暂时停止的容器。
- 镜像仓库是否仍然可用。
- 重新拉取是否会影响恢复时间。

查看镜像与容器关系：

```bash
docker ps -a --format \
  'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

## 17. 安全清理停止容器

查看停止容器：

```bash
docker ps -a \
  --filter status=exited
```

清理停止容器：

```bash
docker container prune
```

删除前应确认：

- 是否需要保留故障日志。
- 容器可写层中是否存在重要文件。
- 容器是否用于临时回滚。
- 数据是否已经放入数据卷。
- 容器配置是否可以重新创建。

## 18. 安全清理数据卷

查看未使用数据卷：

```bash
docker volume ls -f dangling=true
```

清理未被容器引用的数据卷：

```bash
docker volume prune
```

`dangling` 或未被当前容器引用，不代表数据一定没有业务价值。数据库容器被删除后，其数据卷可能变成未使用状态，但其中仍包含重要数据。

清理前应执行：

```bash
docker volume inspect <数据卷名称>
```

并检查实际内容、归属和备份情况。

## 19. 安全清理构建缓存

清理构建缓存：

```bash
docker builder prune
```

清理全部未使用构建缓存：

```bash
docker builder prune -a
```

Buildx 环境可以执行：

```bash
docker buildx prune
```

构建缓存通常不包含运行中的业务数据，但清理后下次构建需要重新下载依赖和执行构建步骤。

## 20. docker system prune 使用注意事项

基础清理：

```bash
docker system prune
```

更大范围清理：

```bash
docker system prune -a
```

包含数据卷的清理：

```bash
docker system prune -a --volumes
```

不建议在生产环境中未经检查直接执行带 `--volumes` 的全量清理，因为可能删除重要业务数据卷。

更安全的方式是分别检查并清理：

1. 停止容器。
2. 悬空镜像。
3. 未使用镜像。
4. 构建缓存。
5. 确认无用的数据卷。

## 21. 临时处理措施

磁盘空间已经接近或达到 100% 时，可以采取：

1. 暂停持续写入大量数据的非核心容器。
2. 降低应用日志级别。
3. 截断确认可以清理的大型容器日志。
4. 清理悬空镜像。
5. 清理确认无用的停止容器。
6. 清理构建缓存。
7. 转移历史备份和 Dump 文件。
8. 暂停镜像构建任务。
9. 扩容 Docker 数据目录所在磁盘。
10. 将日志和业务数据迁移到独立数据盘。
11. 处理已删除但仍被进程占用的文件。
12. 修复持续产生大量小文件的应用。

确认日志可以清空后，可以使用：

```bash
truncate -s 0 <容器日志路径>
```

不要直接删除正在由 Docker 写入的日志文件。截断前应确认日志保留要求并保存必要内容。

## 22. 永久解决方案

### 22.1 配置日志轮转

为所有容器设置单文件最大大小和保留数量，避免 JSON 日志无限增长。

### 22.2 优化 Dockerfile

- 使用较小基础镜像。
- 使用多阶段构建。
- 删除构建临时文件。
- 合并合理的构建步骤。
- 使用 `.dockerignore`。
- 不将日志和业务数据写入镜像。
- 避免重复安装相同依赖。

### 22.3 使用数据卷保存业务数据

数据库、上传文件和持久化数据应使用数据卷、绑定挂载或外部存储，不应长期保存在容器可写层。

### 22.4 建立镜像保留策略

根据发布和回滚要求保留最近若干版本镜像，定期清理更早版本。

### 22.5 定期清理构建缓存

在 CI/CD 构建节点上设置安全的缓存保留和清理策略。

### 22.6 扩容或迁移 Docker 数据目录

当容量无法满足业务增长时，可以：

- 扩容当前磁盘。
- 为 `/var/lib/docker` 挂载独立数据盘。
- 修改 Docker Root Dir。
- 将数据卷迁移到大容量磁盘。
- 将历史数据迁移到对象存储。

迁移 Docker 数据目录前应停止 Docker 服务、备份数据并验证目标文件系统，不能在运行过程中直接移动文件。

## 23. 不建议直接执行的操作

### 23.1 不建议直接删除 /var/lib/docker

该目录包含镜像、容器、网络和数据卷信息，直接删除会造成严重数据丢失。

### 23.2 不建议手工删除 overlay2 文件

手工删除存储层文件可能导致镜像和容器元数据损坏。

### 23.3 不建议直接清理全部数据卷

数据卷可能保存数据库和业务文件，删除后可能无法恢复。

### 23.4 不建议只清理而不分析增长来源

如果容器日志或业务文件仍然持续增长，磁盘很快会再次被占满。

### 23.5 不建议依赖重启释放空间

重启 Docker 不能自动清理镜像、数据卷和日志，只可能释放部分仍被进程占用的已删除文件。

## 24. 监控与预防建议

建议持续监控：

- Docker 根目录使用量。
- 文件系统磁盘使用率。
- 文件系统剩余容量。
- inode 使用率。
- 镜像总大小。
- 容器可写层大小。
- 容器日志文件大小。
- 数据卷大小。
- 构建缓存大小。
- 磁盘增长速度。
- Docker 清理任务执行结果。
- 大文件数量。
- 已删除但仍被占用的文件。

推荐告警条件包括：

- 磁盘使用率超过 80%。
- 剩余容量低于业务数日增长量。
- inode 使用率超过 80%。
- 单个容器日志超过限制。
- 某个容器可写层快速增长。
- Docker 根目录每日增长异常。
- 构建缓存超过预设容量。
- 数据卷容量突然增加。
- 磁盘预计在短时间内耗尽。

## 25. 推荐排查流程

Docker 磁盘空间不足时，可以按照以下顺序排查：

1. 使用 `df -hT` 确认空间不足的文件系统。
2. 使用 `df -i` 检查 inode。
3. 使用 `docker info` 确认 Docker 根目录。
4. 使用 `docker system df -v` 查看整体占用。
5. 使用 `docker ps -a --size` 查看容器可写层。
6. 检查 Docker 镜像和悬空镜像。
7. 检查容器 JSON 日志。
8. 检查数据卷及其业务归属。
9. 检查 BuildKit 和构建缓存。
10. 使用 `du` 定位 Docker 根目录的大目录。

## 27. 排查结论模板

### 故障现象

Docker 宿主机根分区使用率达到 100%，新容器无法启动，应用日志出现 `No space left on device`。

### 故障确认

通过 `docker system df -v` 和 Docker 根目录统计发现，`/var/lib/docker/containers` 占用大量空间。进一步检查发现某个应用容器的 JSON 日志文件超过 40GB。

### 根本原因

应用因下游服务异常持续打印完整错误堆栈，同时容器使用默认 `json-file` 日志驱动，但没有配置 `max-size` 和 `max-file`，导致日志文件无限增长并占满根分区。

### 临时处理

保存必要日志后，暂停异常请求，安全截断大型容器日志文件，释放磁盘空间并恢复容器运行。

### 永久修复

修复应用重复异常日志问题，为容器配置日志轮转，将单个日志文件限制为 100MB 并保留 5 个文件，同时增加容器日志大小和磁盘增长速度监控。

### 验证结果

修复后持续观察 Docker 根目录和容器日志，日志能够正常轮转，磁盘使用率保持稳定，未再次出现空间快速增长。

## 28. 总结

Docker 磁盘空间不足的主要来源包括镜像、容器可写层、容器日志、数据卷和构建缓存。排查时应先确认 Docker 根目录所在文件系统，再使用 `docker system df -v` 和 `docker ps -a --size` 区分不同资源的占用。

容器日志没有配置轮转是最常见的问题之一。应用反复打印错误时，JSON 日志可能在短时间内占满磁盘。数据库和上传文件没有挂载数据卷，也可能导致容器可写层持续增长。

清理时应优先处理明确无用的停止容器、悬空镜像和构建缓存。数据卷可能包含重要业务数据，不能仅根据“未使用”状态直接删除。`overlay2` 和 Docker 根目录中的文件也不应手工删除。

永久解决方案应包括日志轮转、镜像保留策略、数据卷管理、构建缓存清理和磁盘容量监控。对于持续增长的生产环境，还应将 Docker 数据目录迁移到独立数据盘或进行容量扩展。
