# Linux CPU 使用率过高排查

## 一、问题描述

CPU 使用率过高是 Linux 系统中最常见的性能问题之一。当 CPU 长时间处于高负载状态时，系统响应速度会明显下降，业务接口延迟增加，严重情况下甚至会导致服务不可用。

CPU 使用率过高并不一定意味着系统出现故障，也可能是业务访问量增加、定时任务执行或计算密集型程序运行导致。因此，在处理 CPU 异常时，应首先确认 CPU 消耗是否符合业务预期，再进一步定位具体原因。

---

# 二、典型现象

出现 CPU 使用率过高时，通常会表现出以下现象：

- 系统 Load Average 持续升高。
- top 或 htop 中 CPU 使用率长期超过 80%。
- 某个进程持续占用大量 CPU。
- Web 接口响应时间明显增加。
- SSH 登录变慢，执行命令存在明显延迟。
- Java、MySQL、Docker 等服务运行缓慢。
- 系统上下文切换（Context Switch）次数明显增加。
- CPU Idle 长时间接近 0%。

---

# 三、可能原因

## 1. 业务访问量激增

短时间内大量用户访问系统，导致应用程序需要处理更多请求，从而消耗大量 CPU 资源。

典型场景：

- 秒杀活动
- 定时任务集中执行
- 爬虫大量访问
- DDoS 攻击

---

## 2. 应用程序存在死循环

程序逻辑存在 Bug，导致某个线程持续执行计算，无法退出。

例如：

- 无限循环
- 递归未结束
- 算法复杂度过高

通常表现为单个进程 CPU 持续 100%。

---

## 3. Java Full GC 频繁发生

对于 Java 服务，如果 JVM 不断执行 Full GC，会导致 GC 线程大量占用 CPU。

表现：

- Java 进程 CPU 很高
- GC 日志频繁出现 Full GC
- 接口响应变慢

---

## 4. MySQL 慢 SQL

数据库执行大量全表扫描或复杂 Join，CPU 持续升高。

通常伴随：

- mysqld 进程 CPU 很高
- 查询响应缓慢

---

## 5. Docker 容器异常

某个容器内程序异常运行，持续占用 CPU。

例如：

- 日志死循环
- 无限重试
- Bug 导致线程持续运行

---

## 6. 系统频繁上下文切换

大量线程竞争 CPU，会导致 Context Switch 增加。

虽然 CPU 利用率很高，但真正执行业务的时间较少。

---

## 7. 恶意程序或异常进程

系统可能存在：

- 挖矿程序
- 未知脚本
- 木马程序

这些程序通常会持续占用 CPU。

---

# 四、排查流程

## 第一步：查看整体 CPU 使用情况

执行：

```bash
top
```

重点关注：

- us（用户态 CPU）
- sy（内核态 CPU）
- id（空闲 CPU）
- wa（IO 等待）
- load average

如果：

```text
id < 20%
```

说明 CPU 使用率较高。

---

## 第二步：定位高 CPU 进程

执行：

```bash
top
```

或：

```bash
ps -eo pid,user,comm,%cpu --sort=-%cpu | head
```

查看：

- PID
- CPU%
- 进程名称

确认是哪一个进程占用了 CPU。

---

## 第三步：分析进程类型

根据进程名称判断：

例如：

```text
java
```

说明问题可能发生在 JVM。

例如：

```text
mysqld
```

说明数据库可能存在慢 SQL。

例如：

```text
docker
containerd
```

说明可能是容器异常。

---

## 第四步：查看 CPU 核心使用情况

执行：

```bash
mpstat -P ALL 1
```

观察：

- 是否所有 CPU 都很高
- 是否只有某一个核心接近 100%

如果只有单核占满：

通常说明：

- 单线程程序
- Java 某个线程异常

---

## 第五步：分析线程

对于 Java：

先获取 PID：

```bash
jps -l
```

然后：

```bash
top -Hp <pid>
```

找到 CPU 占用最高的线程。

转换线程 ID：

```bash
printf "%x\n" 线程ID
```

再执行：

```bash
jstack <pid>
```

定位具体代码位置。

---

## 第六步：查看系统负载

执行：

```bash
uptime
```

例如：

```text
load average: 8.21 7.95 7.80
```

如果：

Load Average 长时间高于 CPU 核数，

说明系统负载过高。

---

## 第七步：检查上下文切换

执行：

```bash
vmstat 1
```

重点关注：

```text
cs
```

如果：

Context Switch 很高，

说明线程竞争严重。

---

## 第八步：检查是否存在 IO 等待

继续观察 top：

```text
wa
```

如果：

```text
wa > 20%
```

说明 CPU 并不是瓶颈，

真正的问题可能是磁盘 IO。

---

# 五、常用排查命令

查看整体资源：

```bash
top
```

查看 CPU 核心：

```bash
mpstat -P ALL
```

查看高 CPU 进程：

```bash
ps -eo pid,user,comm,%cpu --sort=-%cpu
```

查看线程：

```bash
top -Hp PID
```

查看系统负载：

```bash
uptime
```

查看上下文切换：

```bash
vmstat 1
```

查看进程树：

```bash
pstree -p
```

查看 Docker 容器：

```bash
docker stats
```

# 六、判断依据

| 现象                    | 可能原因                       |
| ----------------------- | ------------------------------ |
| 单个 Java 进程 CPU 很高 | Java 死循环、Full GC、线程异常 |
| mysqld CPU 很高         | 慢 SQL、索引失效               |
| docker CPU 很高         | 容器程序异常                   |
| CPU Idle 很低           | CPU 资源不足                   |
| Load 很高但 CPU 不高    | IO 等待或锁竞争                |
| Context Switch 很高     | 线程过多、锁竞争               |
| 某一个 CPU 核长期 100%  | 单线程程序异常                 |

---

# 七、解决方案

根据定位结果采取不同处理方式：

### Java 服务

- 导出线程栈分析。
- 检查死循环。
- 优化 Full GC。
- 优化线程池配置。

---

### MySQL

- 查看慢查询日志。
- 使用 EXPLAIN 分析 SQL。
- 添加索引。
- 优化查询语句。

---

### Docker

- 查看容器日志。
- 检查容器资源限制。
- 重启异常容器。

---

### Linux

- 停止异常进程。
- 调整业务访问策略。
- 扩容 CPU。
- 优化程序算法。

---

# 八、预防建议

- 建立 CPU 使用率监控，设置合理告警阈值。
- 定期分析慢 SQL 和热点接口。
- 为 Java 服务开启 GC 日志。
- 使用线程池控制并发数量。
- 合理设置 Docker CPU 限制。
- 避免长时间运行高计算任务。
- 定期巡检系统负载和资源使用情况。

---

# 九、相关知识

CPU 使用率异常通常与应用程序、数据库、JVM 或容器运行状态密切相关。在实际生产环境中，应遵循“先定位高 CPU 进程，再分析具体原因”的原则，而不是直接重启服务。对于 Java 应用，可结合 `jstack`、`jmap` 等工具进一步定位线程问题；对于数据库，应结合慢查询日志和执行计划分析 SQL；对于 Docker 环境，应结合 `docker stats` 和容器日志分析资源占用情况。建立完善的监控和告警体系，可以有效降低 CPU 异常对业务的影响。
