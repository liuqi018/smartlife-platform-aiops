# JVM 线程池耗尽排查

## 1. 问题概述

线程池耗尽是指线程池中的工作线程全部被占用，同时新的任务持续进入，导致任务在线程池队列中等待、被拒绝或长时间无法执行。

线程池耗尽并不一定表示线程数量已经达到 JVM 或操作系统上限。更常见的情况是线程池中的线程被慢 SQL、远程调用、锁等待、文件 IO 或长时间任务占用，无法及时处理新任务。

Java 应用中常见的线程池包括：

- Tomcat、Jetty、Undertow 等 Web 线程池。
- `ThreadPoolExecutor` 业务线程池。
- `ScheduledThreadPoolExecutor` 定时任务线程池。
- `ForkJoinPool`。
- `CompletableFuture` 使用的公共线程池。
- 数据库连接池等待线程。
- Netty EventLoop 线程。
- 消息队列消费者线程池。
- RPC 框架业务线程池。
- 异步日志线程池。

线程池耗尽后，应用进程通常仍然存在，但接口响应会越来越慢，最终出现请求超时、任务拒绝和服务不可用。

## 2. 常见问题现象

线程池耗尽时，通常会出现以下现象：

1. 接口请求大量超时。
2. 新请求长时间没有得到处理。
3. Web 服务器工作线程达到最大值。
4. 业务线程池活跃线程数长期等于最大线程数。
5. 任务队列长度持续增长。
6. 应用日志中出现任务拒绝异常。
7. 消息消费速度明显下降。
8. 定时任务延迟或不再执行。
9. CPU 使用率不一定高。
10. Java 进程仍然运行，但健康检查失败。
11. 大量线程停留在网络读取、数据库查询或锁等待位置。
12. 数据库连接池同时出现连接获取超时。
13. 下游服务故障时，本服务线程数量快速增加。
14. 重启服务后暂时恢复，随后再次出现。
15. 容器存活检查失败并被反复重启。

常见异常如下：

```text
java.util.concurrent.RejectedExecutionException
```

```text
Task rejected from java.util.concurrent.ThreadPoolExecutor
```

```text
Timeout waiting for connection from pool
```

```text
Unable to acquire JDBC Connection
```

```text
Connection pool exhausted
```

线程池耗尽与 CPU 过高、死锁、数据库连接池耗尽的表现可能相似，需要结合线程池指标和线程 Dump 判断。

## 3. ThreadPoolExecutor 执行流程

`ThreadPoolExecutor` 的主要参数包括：

```text
corePoolSize
maximumPoolSize
keepAliveTime
workQueue
threadFactory
RejectedExecutionHandler
```

任务提交后的基本流程如下：

```text
提交任务
    ↓
当前线程数是否小于核心线程数
    ├── 是：创建核心线程执行任务
    └── 否：尝试加入任务队列
             ├── 队列未满：进入队列等待
             └── 队列已满：当前线程数是否小于最大线程数
                            ├── 是：创建非核心线程执行任务
                            └── 否：执行拒绝策略
```

需要特别注意：线程池通常不是一达到核心线程数就立即扩展到最大线程数，而是优先把新任务加入队列。只有队列已满后，才会继续创建非核心线程。

如果使用无界队列，队列通常不会被填满，因此 `maximumPoolSize` 可能基本不起作用，任务会持续堆积在内存中。

## 4. 线程池耗尽的常见原因

### 4.1 下游服务响应缓慢

线程发起 HTTP、RPC、Redis 或数据库请求后，需要等待下游响应。如果没有合理设置超时，大量线程可能长期阻塞。

常见场景包括：

- 下游接口响应变慢。
- 数据库慢查询。
- Redis 阻塞。
- 消息队列服务异常。
- DNS 解析缓慢。
- 网络丢包或重传。
- 连接超时时间设置过长。
- 读取超时没有配置。

### 4.2 数据库连接池耗尽

工作线程获取不到数据库连接时，会在连接池中等待。随着等待线程增多，Web 线程池或业务线程池也可能逐渐耗尽。

常见原因包括：

- 数据库连接泄漏。
- 慢 SQL。
- 长事务。
- 数据库连接池过小。
- 数据库最大连接数不足。
- 数据库锁等待。
- 数据库服务响应缓慢。

### 4.3 线程死锁或严重锁竞争

线程之间形成死锁，或者大量线程等待同一把锁，会导致工作线程无法完成任务。

线程栈中通常会出现大量：

```text
java.lang.Thread.State: BLOCKED
```

### 4.4 任务执行时间过长

线程池原本用于处理短任务，但实际提交了大文件处理、批量计算、数据导出、报表生成等长任务，导致线程被长期占用。

### 4.5 任务提交速度过快

任务生产速度长期大于消费速度，线程池和队列会逐渐达到上限。

常见场景包括：

- 突发业务流量。
- 消息积压后集中消费。
- 定时任务一次提交大量子任务。
- 接口没有限流。
- 失败任务被快速重试。
- 上游调用次数突然增加。

### 4.6 线程池参数配置不合理

常见配置问题包括：

- 核心线程数过小。
- 最大线程数过小。
- 队列容量过小。
- 使用无界队列。
- 拒绝策略不合理。
- CPU 密集型和 IO 密集型任务混用。
- 多个业务共用一个线程池。
- 线程池未配置监控。

### 4.7 拒绝策略导致递归提交

任务被拒绝后，如果代码立即重新提交到同一个线程池，可能形成高速重试，加重线程池压力。

### 4.8 线程池内部同步等待子任务

线程池中的任务向同一个线程池提交子任务，并同步等待子任务完成。如果工作线程全部被父任务占用，子任务将永远得不到执行。

常见等待方式包括：

```java
future.get();
```

```java
countDownLatch.await();
```

```java
completableFuture.join();
```

### 4.9 无限创建线程池

应用反复创建线程池但没有关闭，可能导致线程数量持续增长，最终耗尽系统线程、内存或调度资源。

## 5. 排查前的注意事项

发生线程池耗尽时，不要立即重启服务。应先保留以下信息：

1. 至少三次线程 Dump。
2. 线程池核心参数。
3. 活跃线程数。
4. 当前线程数。
5. 任务队列长度。
6. 已完成任务数。
7. 拒绝任务数。
8. 数据库连接池状态。
9. 下游接口耗时。
10. 问题发生时的流量。
11. 最近发布和配置变更。

连续采集线程 Dump：

```bash
jstack -l <PID> > /tmp/jstack-1.txt
sleep 5
jstack -l <PID> > /tmp/jstack-2.txt
sleep 5
jstack -l <PID> > /tmp/jstack-3.txt
```

多次采集可以判断线程是短暂等待，还是长期停留在相同位置。

## 6. 第一步：确认 Java 进程和系统状态

查看 Java 进程：

```bash
jps -lv
```

查看系统负载：

```bash
top
```

查看 Java 进程线程数量：

```bash
ps -o nlwp= -p <PID>
```

也可以执行：

```bash
ls /proc/<PID>/task | wc -l
```

线程池耗尽时 CPU 可能出现以下不同情况：

- CPU 较低：线程可能在等待数据库、网络、锁或文件 IO。
- CPU 较高：线程可能正在执行大量计算。
- IO Wait 较高：线程可能被磁盘 IO 阻塞。
- Load Average 较高：可能存在大量运行或不可中断等待线程。

## 7. 第二步：检查线程池监控指标

如果应用已经暴露线程池监控，应重点查看：

- `corePoolSize`。
- `maximumPoolSize`。
- `poolSize`。
- `activeCount`。
- `largestPoolSize`。
- `queueSize`。
- `queueRemainingCapacity`。
- `taskCount`。
- `completedTaskCount`。
- `rejectedTaskCount`。
- 任务平均执行时间。
- 任务最大执行时间。
- 任务队列等待时间。

典型线程池耗尽特征如下：

```text
activeCount = maximumPoolSize
queueRemainingCapacity = 0
rejectedTaskCount 持续增加
```

如果使用无界队列，可能表现为：

```text
activeCount = corePoolSize
queueSize 持续增加
maximumPoolSize 始终未达到
```

这是因为无界队列不会被填满，线程池不会继续创建非核心线程。

## 8. 第三步：获取线程 Dump

使用 `jstack`：

```bash
jstack -l <PID> > /tmp/jstack.txt
```

使用 `jcmd`：

```bash
jcmd <PID> Thread.print -l > /tmp/thread.txt
```

如果工具无法附加，可以执行：

```bash
kill -3 <PID>
```

`kill -3` 通常不会终止 JVM，而是将线程 Dump 输出到标准错误或应用日志。

查看线程状态分布：

```bash
grep 'java.lang.Thread.State' /tmp/jstack.txt | sort | uniq -c
```

常见线程状态包括：

- `RUNNABLE`。
- `BLOCKED`。
- `WAITING`。
- `TIMED_WAITING`。

线程池耗尽的关键不是某一种状态数量多，而是确认工作线程都在做什么，以及为什么长时间不能完成任务。

## 9. 第四步：根据线程名称定位线程池

线程池通常会通过线程名称区分用途，例如：

```text
http-nio-8080-exec-1
pool-1-thread-1
taskExecutor-1
ForkJoinPool.commonPool-worker-1
scheduled-task-1
DubboServerHandler
NettyServerWorker
```

统计线程名称：

```bash
grep '^"' /tmp/jstack.txt | sort | uniq -c | sort -nr | head -50
```

搜索 Tomcat 工作线程：

```bash
grep -A 30 '"http-nio-.*-exec-' /tmp/jstack.txt
```

搜索自定义线程池：

```bash
grep -A 30 '"taskExecutor-' /tmp/jstack.txt
```

建议在线程工厂中设置具有业务含义的线程名称，例如：

```text
order-query-
report-export-
message-consumer-
```

清晰的线程名称可以显著降低排查难度。

## 10. 第五步：分析工作线程阻塞位置

### 10.1 等待数据库

线程栈可能出现：

```text
com.mysql.cj.jdbc
org.postgresql
PreparedStatement.execute
SocketInputStream.socketRead
```

应继续检查：

- 慢 SQL。
- 数据库锁等待。
- 长事务。
- 数据库负载。
- 连接池状态。
- SQL 超时配置。

### 10.2 等待 HTTP 或 RPC

线程栈可能出现：

```text
java.net.SocketInputStream
sun.nio.ch.SocketDispatcher
okhttp3
org.apache.http
Feign
Dubbo
```

应继续检查：

- 下游服务是否正常。
- 连接超时和读取超时。
- 下游接口耗时。
- DNS 和网络状态。
- 是否存在大量重试。
- 连接池是否耗尽。

### 10.3 等待锁

线程栈可能出现：

```text
java.lang.Thread.State: BLOCKED
```

或者：

```text
LockSupport.park
AbstractQueuedSynchronizer
ReentrantLock
```

应检查锁持有者、锁范围、死锁和热点锁竞争。

### 10.4 等待子任务

线程栈可能出现：

```text
FutureTask.get
CompletableFuture.join
CountDownLatch.await
ForkJoinTask.join
```

应检查是否将子任务提交到同一个已经耗尽的线程池。

### 10.5 执行 CPU 密集任务

线程处于 `RUNNABLE`，并长期停留在：

- 大量循环。
- JSON 处理。
- 正则表达式。
- 加密和压缩。
- 图片和文件处理。
- 大型集合计算。

此时应同时排查 Java 进程 CPU 过高问题。

## 11. 第六步：连续对比线程 Dump

多次线程 Dump 中，如果相同工作线程始终停留在相同代码位置，说明任务可能长期阻塞或执行时间过长。

重点对比：

- 线程名称是否相同。
- 线程状态是否相同。
- 栈顶方法是否相同。
- 是否一直等待相同锁。
- 是否一直等待同一远程地址。
- 是否有任务完成并被新任务替换。
- 工作线程数量是否已经达到上限。

如果线程栈不断变化，说明线程池仍在处理任务，只是整体吞吐量不足。如果线程栈长期不变，则更可能存在阻塞、死锁或无限等待。

## 12. 第七步：检查 Web 线程池

以 Tomcat 为例，常见配置包括：

```properties
server.tomcat.threads.max=200
server.tomcat.threads.min-spare=10
server.tomcat.accept-count=100
server.tomcat.max-connections=8192
```

需要关注：

- 最大工作线程数。
- 当前活跃线程数。
- 等待队列长度。
- 最大连接数。
- 请求处理时间。
- 超时请求数量。

如果所有 Web 线程都在等待下游服务，单纯增加 `threads.max` 可能使更多请求进入系统，进一步增加数据库或下游压力。

Web 请求线程中不应长时间执行大文件处理、批量计算和报表生成等任务。这类任务应拆分为异步任务，并设置独立线程池。

## 13. 第八步：检查数据库连接池

常见数据库连接池包括 HikariCP、Druid 和 DBCP。

应重点监控：

- 最大连接数。
- 活跃连接数。
- 空闲连接数。
- 等待连接线程数。
- 连接获取耗时。
- 连接超时次数。
- 连接泄漏告警。

HikariCP 常见配置包括：

```properties
maximumPoolSize
minimumIdle
connectionTimeout
idleTimeout
maxLifetime
leakDetectionThreshold
```

如果线程 Dump 中大量线程等待获取连接，应检查：

1. 是否存在连接泄漏。
2. SQL 是否执行过慢。
3. 事务是否过长。
4. 数据库最大连接数是否不足。
5. 连接池是否配置过小。
6. 数据库是否发生锁等待。

不能盲目增大连接池。连接数过多可能使数据库负载进一步升高。

## 14. 第九步：检查任务队列

线程池使用有界队列时，需要确认：

- 队列容量是否合理。
- 当前队列长度。
- 队列增长速度。
- 单个任务占用内存。
- 队列满后的拒绝策略。
- 是否存在失败任务重复入队。

线程池使用无界队列时，需要重点防止：

- 任务无限堆积。
- 任务延迟越来越长。
- 大量任务对象进入老年代。
- 最终触发频繁 Full GC 或 OOM。
- `maximumPoolSize` 实际无法发挥作用。

建议根据系统可承载能力设置有界队列，并结合限流、拒绝策略和监控实现过载保护。

## 15. 第十步：检查拒绝策略

常见拒绝策略包括：

### 15.1 AbortPolicy

直接抛出：

```text
RejectedExecutionException
```

适合需要明确感知任务提交失败的场景。

### 15.2 CallerRunsPolicy

由提交任务的线程执行任务，可以降低任务提交速度，形成一定的反压效果。

需要注意，如果提交线程是 Web 请求线程，任务执行时间过长仍可能导致请求线程被占用。

### 15.3 DiscardPolicy

直接丢弃任务，不抛出异常。使用不当可能造成任务静默丢失。

### 15.4 DiscardOldestPolicy

丢弃队列中最旧的任务，再尝试提交新任务。需要确认旧任务是否允许丢失。

选择拒绝策略时应明确：

- 任务是否允许丢失。
- 是否需要重试。
- 是否需要持久化。
- 是否需要返回错误。
- 是否需要触发降级。
- 是否可以通过消息队列削峰。

不应在拒绝后立即无限重试，否则会形成重试风暴。

## 16. 第十一步：检查线程池嵌套调用

典型问题代码：

```java
executor.submit(() -> {
    Future<?> future = executor.submit(this::childTask);
    future.get();
});
```

如果线程池所有线程都在执行父任务，并等待子任务完成，而子任务又只能由同一线程池执行，就可能形成线程池饥饿死锁。

优化方式包括：

- 父任务不阻塞等待子任务。
- 子任务使用独立线程池。
- 使用异步组合。
- 为等待操作设置超时。
- 避免线程池层层嵌套。
- 将任务拆分关系交给统一调度系统管理。

## 17. 第十二步：检查超时和重试配置

网络和数据库调用至少应考虑：

- 连接超时。
- 读取超时。
- 写入超时。
- 请求总超时。
- 线程池排队超时。
- 最大重试次数。
- 重试间隔。
- 指数退避。
- 熔断和降级。

如果没有读取超时，下游服务连接建立后一直不返回，线程可能被无限占用。

如果重试次数过多，每次原始请求都可能产生多个额外请求，造成线程、连接和下游资源进一步耗尽。

## 18. 常见临时处理措施

线程池耗尽已经影响业务时，可以根据情况采取：

1. 保存线程 Dump 和线程池指标。
2. 暂停异常定时任务。
3. 限制高耗时接口流量。
4. 暂停失败任务的自动重试。
5. 降低消息消费并发度。
6. 将故障实例从负载均衡中摘除。
7. 将流量切换到健康实例。
8. 恢复异常的数据库或下游服务。
9. 增加应用实例分担请求。
10. 保存现场后滚动重启故障实例。
11. 对非核心功能进行降级。
12. 对上游请求实施快速失败。

重启只能清理当前阻塞线程，不能修复慢 SQL、连接泄漏或下游超时等根本问题。

## 19. 永久解决方案

### 19.1 设置合理超时

为数据库、HTTP、RPC 和任务等待配置连接超时、读取超时和总超时，避免线程无限等待。

### 19.2 隔离不同任务

将不同性质的任务放入独立线程池：

- Web 请求。
- 数据库任务。
- 远程调用。
- 文件处理。
- 报表导出。
- 消息消费。
- 定时任务。

一个业务线程池耗尽时，不应拖垮所有功能。

### 19.3 使用有界队列

通过有界队列限制系统中等待执行的任务数量，避免任务无限堆积并最终造成 OOM。

### 19.4 优化慢任务

- 优化慢 SQL。
- 缩小事务范围。
- 优化下游接口。
- 大任务分批处理。
- 文件采用流式处理。
- CPU 密集型任务独立部署。
- 避免锁内执行耗时操作。

### 19.5 增加限流、熔断和降级

当系统或下游服务达到容量上限时，应快速拒绝部分请求，而不是让所有请求进入线程池后长时间等待。

### 19.6 修复资源泄漏

- 正确关闭数据库连接。
- 正确关闭 HTTP 响应。
- 释放文件和 Socket。
- 关闭不再使用的线程池。
- 修复 ThreadLocal 泄漏。
- 取消不再需要的定时任务。

## 20. 线程池参数设置建议

线程池参数应根据任务类型、CPU 核心数、任务耗时和下游容量确定。

### 20.1 CPU 密集型任务

线程数通常不宜远高于 CPU 核心数，否则会增加上下文切换。

可以初步参考：

```text
CPU 核心数 + 1
```

实际值需要通过压力测试确定。

### 20.2 IO 密集型任务

线程数可以适当高于 CPU 核心数，因为线程会有较多时间等待 IO。

可以根据以下关系进行估算：

```text
线程数 ≈ CPU 核心数 × （1 + 等待时间 / 计算时间）
```

该公式只能作为初始估算，还需要结合下游服务、连接池和机器资源进行测试。

### 20.3 队列容量

队列容量不应只根据内存设置，还要考虑：

- 允许的最大排队时间。
- 单个任务大小。
- 任务处理速度。
- 突发流量规模。
- 拒绝后的业务策略。
- 下游承载能力。

## 21. 不建议直接执行的操作

### 21.1 不建议盲目增加最大线程数

增加线程数可能加剧：

- CPU 上下文切换。
- 内存占用。
- 数据库连接竞争。
- 下游服务压力。
- 锁竞争。
- 系统调度压力。

### 21.2 不建议使用无界队列解决拒绝

无界队列只是把任务拒绝问题转化为长时间排队和内存问题，最终可能导致 Full GC 或 OOM。

### 21.3 不建议无限增加连接池

线程池和数据库连接池需要匹配。连接数过多可能使数据库负载更高，SQL 执行更慢。

### 21.4 不建议立即重启而不保存现场

重启会清除线程状态和等待关系，导致无法定位真正原因。

### 21.5 不建议只关注线程数量

线程池耗尽的根本原因通常是任务无法及时完成。只调整线程数，不解决慢调用和阻塞问题，故障仍会再次发生。

## 22. 监控与预防建议

建议监控以下指标：

- 核心线程数。
- 最大线程数。
- 当前线程数。
- 活跃线程数。
- 历史最大线程数。
- 队列长度。
- 队列剩余容量。
- 已提交任务数。
- 已完成任务数。
- 拒绝任务数。
- 任务执行时间。
- 任务排队时间。
- Java 总线程数。
- 各线程状态数量。
- 数据库连接池使用率。
- 下游接口响应时间。
- 请求超时率。
- 消息积压数量。
- CPU 和内存使用率。

推荐告警条件包括：

- 活跃线程数长期等于最大线程数。
- 队列长度持续增长。
- 队列剩余容量接近 0。
- 拒绝任务数开始增加。
- 任务排队时间明显升高。
- 数据库连接池等待线程增加。
- 大量线程长期停留在同一下游调用。
- Web 请求线程使用率超过安全阈值。
- 下游超时率和线程池使用率同步升高。

## 23. 推荐排查流程

线程池耗尽可以按照以下顺序排查：

1. 确认发生问题的 Java 进程。
2. 查看系统 CPU、内存和线程数量。
3. 查看线程池核心参数和运行指标。
4. 确认活跃线程是否达到最大值。
5. 检查任务队列是否已满或持续增长。
6. 检查是否出现 `RejectedExecutionException`。
7. 连续获取至少三次线程 Dump。
8. 根据线程名称定位对应线程池。
9. 分析工作线程的主要阻塞位置。
10. 检查数据库慢 SQL和连接池状态。
11. 检查下游接口耗时和超时配置。
12. 检查锁竞争和线程死锁。
13. 检查任务是否同步等待同一线程池中的子任务。
14. 检查定时任务、消息消费和批处理任务。
15. 检查任务提交速度是否超过处理速度。
16. 采取限流、降级、暂停任务或扩容等临时措施。
17. 优化慢任务、超时、线程池和队列配置。
18. 通过压力测试验证处理效果。
19. 增加线程池和下游依赖监控。

## 24. 常用排查命令汇总

```bash
# 查看 Java 进程
jps -lv
ps -ef | grep java

# 查看系统状态
top
uptime
free -h

# 查看 Java 线程数量

# 获取线程 Dump

# 使用 jcmd 获取线程 Dump

# 连续获取线程 Dump
jstack -l <PID> > /tmp/jstack-1.txt
sleep 5
jstack -l <PID> > /tmp/jstack-2.txt
sleep 5
jstack -l <PID> > /tmp/jstack-3.txt

# 统计线程状态
grep 'java.lang.Thread.State' /tmp/jstack.txt | sort | uniq -c

# 查看 BLOCKED 线程
grep -B 2 -A 20 'java.lang.Thread.State: BLOCKED' /tmp/jstack.txt

# 查看线程名称
grep '^"' /tmp/jstack.txt | head -100

# 搜索 Future 等待
grep -B 5 -A 20 -E 'FutureTask.get|CompletableFuture|CountDownLatch.await' /tmp/jstack.txt

# 搜索数据库调用
grep -B 5 -A 20 -E 'jdbc|mysql|postgresql|PreparedStatement' /tmp/jstack.txt

# 搜索网络调用
grep -B 5 -A 20 -E 'SocketInputStream|SocketDispatcher|okhttp|httpclient' /tmp/jstack.txt

# 查看 JVM 参数
jcmd <PID> VM.flags

# 查看 JVM 启动命令
jcmd <PID> VM.command_line

# 查看服务日志

# 查看应用错误日志

```

## 25. 排查结论模板

### 故障现象

订单接口大量超时，Java 进程仍然运行且 CPU 使用率不高，Tomcat 工作线程长期处于满载状态，线程池队列持续增长。

### 故障确认

通过线程池监控发现活跃线程数已经达到最大线程数。连续采集三次线程 Dump 后，发现绝大部分 Web 工作线程都停留在调用库存服务的 HTTP 客户端读取方法中。

### 根本原因

库存服务响应异常缓慢，而订单服务的 HTTP 客户端没有配置合理的读取超时。请求线程建立连接后长期等待响应，导致 Tomcat 工作线程逐渐被全部占用。新请求只能进入等待队列，最终出现大面积接口超时。

### 临时处理

将故障实例从负载均衡中摘除，暂停相关接口流量，恢复库存服务后滚动重启订单服务，使线程池资源恢复正常。

### 永久修复

为 HTTP 客户端配置连接超时、读取超时和总请求超时；增加熔断、限流和降级策略；将库存查询与其他业务任务隔离到独立线程池；增加线程池活跃线程数、队列长度和下游接口耗时监控。

### 验证结果

修复后模拟库存服务延迟和不可用场景，请求能够在设定时间内快速失败并触发降级，Tomcat 工作线程不再持续堆积，线程池拒绝数量保持为 0。

## 26. 总结

JVM 线程池耗尽的本质是任务进入速度长期大于任务完成速度，或者工作线程被慢调用、锁等待和长任务持续占用。

排查时应先查看线程池的活跃线程数、最大线程数、队列长度和拒绝数量，再通过多次线程 Dump 确认工作线程正在执行什么任务。如果大量线程停留在数据库、HTTP、锁或 `Future.get()` 等位置，应继续检查对应的依赖、超时和任务设计。

线程池耗尽不能只通过增加线程数解决。线程数过多会增加内存、上下文切换、数据库连接和下游服务压力。更可靠的解决方式是设置合理超时、使用有界队列、隔离不同任务、优化慢调用，并增加限流、熔断、降级和拒绝处理。

生产环境应为所有关键线程池建立监控，至少覆盖活跃线程数、队列长度、任务执行时间和拒绝数量。在故障发生时，应先保存线程 Dump 和线程池指标，再进行流量切换或滚动重启，避免关键现场丢失。
