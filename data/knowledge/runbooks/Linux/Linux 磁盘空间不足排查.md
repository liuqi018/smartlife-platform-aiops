# Linux 磁盘空间不足排查

## 1. 问题概述

Linux 磁盘空间不足是指磁盘分区、逻辑卷、文件系统或容器存储空间的使用率过高，导致系统或应用程序无法继续写入数据。

磁盘空间不足是 Linux 服务器中较为常见的故障之一。日志文件持续增长、数据库数据量增加、临时文件未清理、Docker 镜像堆积、已删除文件仍被进程占用等问题，都可能导致磁盘空间被耗尽。

当磁盘空间完全耗尽时，操作系统和应用程序可能无法创建新文件、写入日志、保存数据库数据或生成临时文件，严重时还会导致数据库异常、服务启动失败、系统无法登录等问题。

磁盘空间不足不只包括磁盘容量不足，还包括 inode 耗尽。即使磁盘仍然存在可用容量，如果 inode 已经被大量小文件耗尽，系统同样无法创建新文件。因此，排查时需要同时检查磁盘容量和 inode 使用情况。

## 2. 常见问题现象

Linux 磁盘空间不足时，通常会出现以下现象：

1. 应用程序无法正常写入数据。
2. 日志中出现 `No space left on device`。
3. 数据库无法写入、提交事务或创建临时表。
4. 服务无法启动或运行过程中突然退出。
5. 上传文件、生成报表或导出数据失败。
6. 系统无法创建临时文件。
7. 用户无法正常登录服务器。
8. Docker 容器无法启动或创建新容器。
9. 软件安装、升级或解压缩失败。
10. 日志文件停止更新。
11. 磁盘使用率达到 90% 或 100%。
12. 文件系统被自动重新挂载为只读模式。
13. 明明存在剩余容量，却仍然无法创建新文件。
14. 删除文件后，磁盘空间没有立即释放。

常见错误信息如下：

```text
No space left on device
```

```text
write error: No space left on device
```

```text
Failed to write log file
```

```text
Read-only file system
```

```text
Disk quota exceeded
```

这些错误分别可能表示磁盘容量耗尽、inode 耗尽、文件系统只读或者用户磁盘配额达到限制，需要结合系统状态进一步确认。

## 3. 磁盘空间不足的常见原因

### 3.1 日志文件持续增长

应用日志、系统日志、访问日志和错误日志如果没有配置轮转和过期清理，可能持续增长并占满磁盘。

常见日志目录包括：

```text
/var/log
/var/log/messages
/var/log/syslog
/var/log/journal
/var/log/nginx
/var/log/mysql
/var/log/audit
```

应用程序如果持续输出异常堆栈、请求日志或调试日志，日志文件可能在短时间内快速增长。

### 3.2 数据库文件持续增长

MySQL、PostgreSQL、Elasticsearch 等服务会随着业务数据增加持续占用磁盘空间。

除业务数据外，还需要关注：

- MySQL Binary Log。
- MySQL Relay Log。
- MySQL Slow Log。
- PostgreSQL WAL 日志。
- Elasticsearch 索引和事务日志。
- 数据库临时文件。
- 数据库备份文件。
- 未清理的历史表和归档表。

### 3.3 临时文件没有及时清理

程序运行过程中可能在 `/tmp`、`/var/tmp` 或应用临时目录中生成大量临时文件。如果程序异常退出或缺少清理逻辑，这些文件可能长期保留。

常见临时文件包括：

- 上传文件。
- 解压缩文件。
- 报表文件。
- 图片处理文件。
- 视频转码文件。
- 数据导入中间文件。
- 应用缓存。
- 安装包和升级文件。

### 3.4 Docker 数据持续堆积

Docker 会保存镜像、容器可写层、日志、数据卷和构建缓存。如果长期不清理，`/var/lib/docker` 可能占用大量磁盘空间。

常见问题包括：

- 无用镜像过多。
- 已停止容器未删除。
- 容器日志持续增长。
- 无用数据卷未清理。
- Docker 构建缓存过多。
- 容器频繁创建和删除产生残留数据。

### 3.5 已删除文件仍被进程占用

Linux 中，如果文件被删除时仍然被某个进程打开，目录中虽然已经看不到该文件，但文件所占用的磁盘空间不会立即释放。

只有对应进程关闭文件描述符或退出后，空间才会真正释放。这种情况经常发生在日志文件被直接删除，但应用程序仍然继续向原文件描述符写入时。

### 3.6 inode 被大量小文件耗尽

文件系统中的每个文件和目录都需要使用 inode。如果系统中存在大量小文件，可能在磁盘容量尚未用完时就耗尽全部 inode。

常见场景包括：

- Session 文件过多。
- 缓存文件过多。
- 邮件队列文件过多。
- 临时文件过多。
- 应用按照请求生成独立小文件。
- 程序异常产生大量空文件。
- 容器存储层产生大量小文件。

### 3.7 备份文件重复堆积

数据库备份、应用备份、日志归档包和系统快照如果没有设置保留周期，可能不断累积并占满磁盘。

例如：

- 每日全量数据库备份。
- 未清理的增量备份。
- 多个版本的应用发布包。
- 手动复制的历史目录。
- 定时任务重复生成压缩包。
- 备份失败后遗留的中间文件。

### 3.8 磁盘分区规划不合理

服务器磁盘总容量可能仍然充足，但某个独立分区已经被占满。

例如：

- `/var` 分区被日志占满。
- `/home` 分区容量不足。
- `/tmp` 使用独立小分区。
- 数据库目录位于容量较小的根分区。
- Docker 数据目录位于 `/var` 分区。
- 新增磁盘没有挂载到实际业务目录。

### 3.9 文件系统保留空间

ext4 文件系统通常会为 root 用户保留一部分空间。普通用户可能在磁盘使用率尚未完全达到 100% 时，就遇到无法写入的问题。

保留空间能够避免系统关键进程在磁盘接近满载时完全无法运行，但在大容量纯数据盘中，如果保留比例过高，也可能造成大量空间不能被普通用户使用。

### 3.10 用户磁盘配额达到限制

系统如果启用了用户或用户组磁盘配额，某个用户即使面对仍有剩余空间的文件系统，也可能因为达到配额限制而无法继续写入数据。

此时通常会出现：

```text
Disk quota exceeded
```

## 4. 排查前的注意事项

发生磁盘空间不足时，不要直接执行大范围删除操作。删除前应确认文件用途、所属服务、保留要求以及是否可以恢复。

生产环境中应特别注意以下事项：

1. 不要直接删除数据库正在使用的数据文件。
2. 不要随意删除 `/var/lib` 中不清楚用途的目录。
3. 不要直接删除当前正在写入的日志文件。
4. 不要使用范围不明确的通配符批量删除文件。
5. 不要在没有确认目录的情况下执行递归删除。
6. 不要删除系统启动、软件包管理或安全审计相关文件。
7. 删除备份前应确认其他位置存在可用副本。
8. 清理 Docker 数据前应确认容器、镜像和数据卷是否仍在使用。
9. 磁盘已经严重不足时，应避免生成大型排查文件。
10. 操作前尽量记录磁盘状态和大文件信息。

建议先保存以下排查结果：

```bash
date
df -hT
df -i
lsblk -f
mount
du -xhd1 / 2>/dev/null
lsof +L1
```

## 5. 第一步：查看文件系统容量

执行：

```bash
df -h
```

示例输出：

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2        50G   47G  3.0G  95% /
/dev/sdb1       200G  120G   80G  60% /data
```

重点关注：

- `Size`：文件系统总容量。
- `Used`：已经使用的容量。
- `Avail`：普通用户可以使用的剩余容量。
- `Use%`：磁盘空间使用率。
- `Mounted on`：文件系统挂载目录。

如果需要同时查看文件系统类型，可以执行：

```bash
df -hT
```

排查时应先确认具体是哪个挂载点空间不足，而不是直接从根目录开始删除文件。

例如，`/data` 是独立分区时，删除根分区 `/` 下的文件并不能释放 `/data` 的空间。

## 6. 第二步：检查 inode 使用情况

执行：

```bash
df -i
```

示例输出：

```text
Filesystem       Inodes   IUsed   IFree IUse% Mounted on
/dev/sda2       3276800 3276800       0  100% /
```

如果磁盘容量仍有剩余，但 inode 使用率达到 100%，系统同样会提示：

```text
No space left on device
```

inode 耗尽时，需要定位包含大量文件的目录，而不是只查找大文件。

可以使用以下命令统计目录中的文件数量：

```bash
find /目标目录 -xdev -type f | wc -l
```

统计当前目录下各一级子目录的文件数量：

```bash
for dir in /目标目录/*; do
    [ -d "$dir" ] && printf "%s " "$dir" && find "$dir" -xdev -type f | wc -l
done
```

如果目录中文件数量非常多，执行 `find` 可能带来一定的磁盘 IO 压力，应从疑似目录开始逐级排查，避免直接扫描所有文件系统。

## 7. 第三步：定位占用空间较大的目录

### 7.1 使用 du 查看一级目录

如果根分区空间不足，可以执行：

```bash
du -xhd1 / 2>/dev/null | sort -h
```

其中：

- `-x` 表示不跨越其他文件系统。
- `-h` 表示使用可读单位显示。
- `-d1` 表示只统计一级目录。

如果发现 `/var` 占用较大，可以继续执行：

```bash
du -xhd1 /var 2>/dev/null | sort -h
```

然后继续逐级定位：

```bash
du -xhd1 /var/log 2>/dev/null | sort -h
```

推荐按照以下方式逐层缩小范围：

```text
/
/var
/var/log
/var/log/具体服务
```

不要一开始就扫描整个服务器的所有文件，因为大范围 `du` 可能产生较高的磁盘 IO，并且容易受到其他挂载点干扰。

### 7.2 查看目录总大小

```bash
du -sh /目标目录
```

例如：

```bash
du -sh /var/log
du -sh /var/lib/docker
du -sh /data/mysql
```

### 7.3 查看当前目录下各文件和目录大小

```bash
du -sh /目标目录/* 2>/dev/null | sort -h
```

该命令能够快速发现某个目录下占用空间较大的子目录或文件。

## 8. 第四步：查找大文件

查找指定文件系统中大于 1GB 的文件：

```bash
find /目标目录 -xdev -type f -size +1G -print
```

显示文件大小并排序：

```bash
find /目标目录 -xdev -type f -size +500M -printf '%s %p\n' 2>/dev/null | sort -nr | head -50
```

如果系统中的 `find` 不支持 `-printf`，可以先使用：

```bash
find /目标目录 -xdev -type f -size +500M -ls 2>/dev/null
```

常见的大文件包括：

- 应用日志。
- 数据库日志。
- 数据库数据文件。
- Core Dump。
- Heap Dump。
- 安装包。
- 压缩包。
- 虚拟机镜像。
- Docker 容器日志。
- 备份文件。
- 临时导出文件。

找到大文件后，不要立即删除，应先确认文件是否仍在使用、是否需要保留以及是否可以压缩或转移。

## 9. 第五步：排查已删除但仍被占用的文件

执行：

```bash
lsof +L1
```

也可以执行：

```bash
lsof | grep deleted
```

示例：

```text
java  12345 app  10w  REG  8,2  10737418240  0  123456 /var/log/app.log (deleted)
```

该结果说明 `/var/log/app.log` 虽然已经从目录中删除，但 PID 为 `12345` 的 Java 进程仍然打开该文件，并占用约 10GB 磁盘空间。

这时使用 `du` 可能已经看不到该文件，但 `df` 显示的磁盘空间仍然没有释放，从而出现 `df` 和 `du` 结果差异较大的情况。

常见处理方式包括：

1. 让应用程序重新打开日志文件。
2. 正常重启对应服务。
3. 通过日志轮转工具通知进程重新打开文件。
4. 在明确了解影响后清空对应文件描述符。

优先选择正常重启或通知进程重新打开文件。直接操作 `/proc/<PID>/fd/` 下的文件描述符存在风险，处理前必须确认文件描述符对应的文件和业务影响。

## 10. 第六步：排查日志文件

查看 `/var/log` 下各目录和文件大小：

```bash
du -sh /var/log/* 2>/dev/null | sort -h
```

查找大于 500MB 的日志文件：

```bash
find /var/log -type f -size +500M -ls 2>/dev/null
```

查看 systemd journal 占用：

```bash
journalctl --disk-usage
```

查看日志轮转配置：

```bash
cat /etc/logrotate.conf
```

查看具体轮转规则：

```bash
ls -l /etc/logrotate.d/
```

日志文件持续增长时，应检查以下问题：

- 是否启用了日志轮转。
- 轮转配置是否执行成功。
- 日志保留周期是否过长。
- 单个日志文件大小限制是否合理。
- 应用是否开启了 Debug 日志。
- 是否存在异常请求导致日志爆发。
- 应用是否持续打印重复异常。
- 压缩后的历史日志是否及时清理。
- 日志采集程序是否正常读取和转储日志。

对于当前正在写入的日志文件，不建议直接执行 `rm`。可以根据应用支持情况，通过日志轮转、重新打开日志文件或安全截断的方式处理。

安全截断普通日志文件的常见方式为：

```bash
truncate -s 0 /path/to/application.log
```

执行前必须确认该文件只是可清理的日志文件，不是数据库文件、索引文件或其他业务数据文件。

## 11. 第七步：排查 systemd journal 日志

部分 Linux 系统使用 systemd-journald 保存日志，日志通常存放在：

```text
/var/log/journal
```

查看占用空间：

```bash
journalctl --disk-usage
```

按时间清理历史日志：

```bash
journalctl --vacuum-time=7d
```

按照最大容量清理：

```bash
journalctl --vacuum-size=1G
```

可以在以下配置文件中设置长期限制：

```text
/etc/systemd/journald.conf
```

常见配置项包括：

```ini
SystemMaxUse=1G
SystemKeepFree=2G
MaxRetentionSec=7day
```

修改配置后，可以重启 journald：

```bash
systemctl restart systemd-journald
```

清理前应确认日志保留要求，特别是涉及安全审计、故障追踪和合规要求的服务器。

## 12. 第八步：排查 Docker 磁盘占用

查看 Docker 整体磁盘使用情况：

```bash
docker system df
```

查看详细信息：

```bash
docker system df -v
```

查看 Docker 数据目录大小：

```bash
du -sh /var/lib/docker
```

Docker 常见磁盘占用来源包括：

- Docker 镜像。
- 已停止容器。
- 容器可写层。
- Docker 数据卷。
- Build Cache。
- 容器标准输出日志。

查看容器日志大小：

```bash
find /var/lib/docker/containers -name '*-json.log' -type f -ls 2>/dev/null
```

Docker 默认的 `json-file` 日志驱动如果没有设置日志轮转，容器日志可能持续增长。

可以在 Docker Compose 中设置：

```yaml
services:
  app:
    logging:
      driver: json-file
      options:
        max-size: "100m"
        max-file: "5"
```

也可以在 Docker 守护进程配置中设置日志限制：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "5"
  }
}
```

清理 Docker 资源前，应先确认资源是否仍然被业务使用。以下命令可能删除无用资源，但不能在未确认影响时直接执行：

```bash
docker image prune
docker container prune
docker volume prune
docker builder prune
docker system prune
```

特别是数据卷中可能保存数据库或业务文件，清理数据卷前必须确认其用途和关联关系。

## 13. 第九步：排查数据库磁盘占用

### 13.1 MySQL

MySQL 常见磁盘占用来源包括：

- 表数据文件。
- Binary Log。
- Relay Log。
- Slow Query Log。
- General Log。
- 临时文件。
- 备份文件。
- 错误日志。

查看 MySQL 数据目录：

```bash
du -sh /var/lib/mysql
```

查看数据目录下各文件大小：

```bash
du -sh /var/lib/mysql/* 2>/dev/null | sort -h
```

如果 Binary Log 占用过多，应通过 MySQL 管理命令和过期策略进行清理，不要直接在文件系统中删除正在使用的 Binlog 文件。

可以检查相关配置：

```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
SHOW BINARY LOGS;
```

### 13.2 PostgreSQL

PostgreSQL 常见磁盘占用来源包括：

- 数据表文件。
- WAL 日志。
- 临时文件。
- 归档日志。
- 未及时回收的历史版本。
- 数据库备份。

如果 `pg_wal` 持续增长，应检查复制槽、从库状态、归档配置和长事务，不能直接删除 WAL 文件。

### 13.3 Elasticsearch

Elasticsearch 常见磁盘占用来源包括：

- 索引分片。
- 副本分片。
- Translog。
- 快照缓存。
- 历史索引。
- 异常分片迁移产生的数据。

应通过 Elasticsearch API 删除或迁移索引，不要直接删除数据目录中的索引文件。

## 14. 第十步：排查临时文件和缓存

常见临时目录包括：

```text
/tmp
/var/tmp
/var/cache
```

查看目录大小：

```bash
du -sh /tmp
du -sh /var/tmp
du -sh /var/cache
```

查看较大的临时文件：

```bash
find /tmp -xdev -type f -size +100M -ls 2>/dev/null
```

查看长时间未修改的临时文件：

```bash
find /tmp -xdev -type f -mtime +7 -ls 2>/dev/null
```

不能仅根据文件修改时间直接删除。某些程序可能长期使用临时文件，删除前应通过 `lsof` 或业务配置确认文件是否仍在使用。

如果系统使用 `systemd-tmpfiles`，可以检查：

```bash
systemd-tmpfiles --cat-config
```

## 15. 第十一步：排查备份文件和归档文件

查找常见的备份与压缩文件：

```bash
find /目标目录 -xdev -type f \( -name '*.tar' -o -name '*.tar.gz' -o -name '*.zip' -o -name '*.bak' -o -name '*.sql' -o -name '*.dump' \) -ls 2>/dev/null
```

重点检查：

- 数据库全量备份。
- 数据库增量备份。
- 应用发布包。
- 日志压缩包。
- 系统镜像。
- 手动复制的目录。
- 定时任务生成的归档文件。
- 上传后未转移的文件。

建议为备份任务设置明确的保留策略，例如：

- 每日备份保留 7 天。
- 每周备份保留 4 周。
- 每月备份保留 6 个月。
- 重要备份转移到独立存储。
- 清理前验证最近备份是否可用。

## 16. 第十二步：检查磁盘挂载情况

执行：

```bash
lsblk -f
```

查看挂载点：

```bash
mount
```

查看文件系统配置：

```bash
cat /etc/fstab
```

磁盘空间问题有时不是数据增长导致的，而是磁盘没有正确挂载。

例如，原本 `/data` 应该挂载独立数据盘，但数据盘挂载失败后，应用仍然向 `/data` 写入数据。此时数据实际上写入了根分区，最终导致根分区被占满。

排查时需要确认：

- 数据盘是否正常挂载。
- 当前挂载点是否与配置一致。
- 重启后挂载是否失效。
- 网络文件系统是否断开。
- 应用写入目录是否位于预期分区。
- 挂载前目录中是否已经存在历史文件。

如果挂载点目录中原本存在文件，挂载磁盘后这些文件会被暂时隐藏。需要在确保业务安全的情况下卸载文件系统后，才能检查被挂载点遮挡的原目录内容。

## 17. 第十三步：检查文件系统是否只读

如果日志中出现：

```text
Read-only file system
```

应执行：

```bash
mount | grep ' ro[,)]'
```

也可以查看内核日志：

```bash
dmesg -T | tail -100
```

文件系统可能因为磁盘故障、文件系统错误或异常断电而被内核重新挂载为只读模式。

此时不能只按照普通的磁盘空间不足处理，应继续检查：

- 磁盘是否存在 IO 错误。
- 文件系统是否损坏。
- 存储设备是否异常。
- RAID 是否降级。
- 云磁盘是否出现故障。
- 是否需要在维护窗口执行文件系统检查。

对于正在使用的文件系统，特别是根文件系统，不应直接在线执行高风险修复操作。

## 18. 第十四步：检查磁盘配额

如果错误信息为：

```text
Disk quota exceeded
```

可以检查用户磁盘配额：

```bash
quota -u <用户名>
```

查看文件系统配额报告：

```bash
repquota -a
```

磁盘配额问题需要确认：

- 用户是否达到容量软限制或硬限制。
- 用户是否达到 inode 配额限制。
- 宽限期是否已经结束。
- 应用是否使用了错误的系统用户运行。
- 配额是否满足当前业务数据规模。

## 19. df 与 du 结果不一致的原因

排查时经常会遇到 `df` 显示磁盘已满，但 `du` 统计出的文件总量明显较小。

常见原因包括：

### 19.1 已删除文件仍被进程占用

文件已经被删除，但进程仍然持有文件描述符。此时 `du` 无法看到文件，而 `df` 仍然统计其占用空间。

排查命令：

```bash
lsof +L1
```

### 19.2 挂载点隐藏了原目录文件

目录中原本存在文件，之后又在该目录上挂载了其他文件系统。原文件被挂载点遮挡，普通情况下无法直接看到，但仍然占用下层文件系统空间。

### 19.3 文件系统保留空间

ext4 等文件系统会为 root 用户保留部分空间，导致 `df` 中普通用户可用空间小于实际剩余空间。

### 19.4 稀疏文件

稀疏文件的逻辑大小和实际占用空间可能不同。`ls -lh` 显示的文件大小不一定等于实际磁盘占用。

可以对比：

```bash
ls -lh /path/to/file
du -h /path/to/file
```

### 19.5 du 没有足够权限

普通用户执行 `du` 时，可能因为无权访问部分目录而漏掉数据。应检查命令输出中的权限错误，并在授权范围内使用具备相应权限的账号排查。

## 20. 磁盘空间不足的处理措施

### 20.1 临时止损措施

当磁盘使用率已经接近或达到 100% 时，可以采取以下临时措施：

1. 暂停产生大量文件的非核心任务。
2. 临时降低应用日志级别。
3. 清理确认无用的历史日志。
4. 清理过期临时文件。
5. 转移历史备份和归档文件。
6. 清理确认无用的 Docker 镜像和容器。
7. 截断确认可以清空的大型日志文件。
8. 重启占用已删除文件的进程。
9. 扩容云磁盘或逻辑卷。
10. 将新增数据临时写入其他磁盘。

临时清理后，应尽快完成根本原因分析，避免磁盘再次被写满。

### 20.2 配置日志轮转

使用 `logrotate` 对日志进行轮转、压缩和过期清理。

示例配置：

```text
/var/log/example/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

配置含义如下：

- `daily`：每天轮转。
- `rotate 7`：保留 7 个历史文件。
- `compress`：压缩历史日志。
- `delaycompress`：延迟一个周期压缩。
- `missingok`：日志不存在时不报错。
- `notifempty`：空日志不轮转。
- `copytruncate`：复制后清空原文件。

`copytruncate` 可能造成极短时间内的日志丢失。更可靠的方式是让应用在日志轮转后重新打开文件，具体应根据应用和日志框架选择。

### 20.3 扩容文件系统

如果磁盘容量确实无法满足业务增长，可以考虑：

- 扩容云磁盘。
- 扩容 LVM 逻辑卷。
- 新增数据盘。
- 迁移大目录到独立磁盘。
- 将历史数据迁移到对象存储。
- 调整数据库冷热数据存储策略。

扩容磁盘后，还需要根据文件系统类型扩展分区、逻辑卷和文件系统。不能只在云平台扩大磁盘容量而不扩展操作系统中的文件系统。

### 20.4 优化业务数据保留策略

根据业务要求设置合理的数据生命周期：

- 在线数据保留必要周期。
- 历史数据定期归档。
- 无效数据定期删除。
- 大文件迁移到对象存储。
- 数据库历史表进行分区或归档。
- 日志和备份设置明确保留天数。
- 临时文件在任务结束后自动清理。

## 21. 监控与预防建议

建议监控以下指标：

- 各文件系统磁盘使用率。
- 各文件系统剩余容量。
- inode 使用率。
- 磁盘空间增长速度。
- 主要目录容量。
- 日志文件增长速度。
- Docker 数据目录容量。
- 数据库数据目录容量。
- 备份目录容量。
- 已删除但仍被占用的文件。
- 文件系统只读状态。
- 磁盘配额使用率。

磁盘告警可以设置多个级别，例如：

- 使用率达到 80%：提醒关注。
- 使用率达到 90%：需要处理。
- 使用率达到 95%：严重告警。
- inode 使用率达到 90%：严重告警。
- 剩余空间低于业务单日增长量的数倍：提前扩容。

不能只按照固定使用率告警。对于容量很大的磁盘，即使只剩 5%，也可能仍有大量空间；对于容量较小但数据增长很快的磁盘，即使当前使用率只有 80%，也可能在数小时内被写满。因此，还应结合剩余容量和增长速度进行预测。

## 22. 推荐排查流程

发生 Linux 磁盘空间不足时，可以按照以下顺序排查：

1. 使用 `df -hT` 确认空间不足的文件系统和挂载点。
2. 使用 `df -i` 检查是否为 inode 耗尽。
3. 使用 `lsblk -f` 和 `mount` 确认磁盘挂载是否正常。
4. 使用 `du -xhd1` 从对应挂载点开始逐级定位大目录。
5. 使用 `find` 查找大文件和大量小文件。
6. 使用 `lsof +L1` 检查已删除但仍被进程占用的文件。
7. 检查应用日志、系统日志和 journald 日志。
8. 检查数据库数据、事务日志和备份文件。
9. 检查 Docker 镜像、容器、数据卷和容器日志。
10. 检查临时目录、缓存目录和历史发布包。
11. 检查文件系统是否变为只读。
12. 检查用户磁盘配额和文件系统保留空间。
13. 采取安全的临时清理、文件转移或扩容措施。
14. 配置日志轮转、数据归档和自动清理策略。
15. 增加磁盘容量、inode 和增长趋势监控。

## 23. 常用排查命令汇总

```bash
# 查看文件系统容量
df -h

# 查看文件系统类型
df -hT

# 查看 inode 使用情况
df -i

# 查看磁盘和文件系统
lsblk -f

# 查看挂载信息
mount

# 查看根目录下一级目录大小
du -xhd1 / 2>/dev/null | sort -h

# 查看指定目录下一级目录大小
du -xhd1 /目标目录 2>/dev/null | sort -h

# 查看目录总大小
du -sh /目标目录

# 查找大于 1GB 的文件
find /目标目录 -xdev -type f -size +1G -ls 2>/dev/null

# 查看已删除但仍被进程占用的文件
lsof +L1

# 查看日志目录占用
du -sh /var/log/* 2>/dev/null | sort -h

# 查看 journald 日志占用
journalctl --disk-usage

# 查看 Docker 磁盘使用
docker system df

# 查看 Docker 详细磁盘使用
docker system df -v

# 查找 Docker 大型日志
find /var/lib/docker/containers -name '*-json.log' -type f -ls 2>/dev/null

# 查看临时目录大小
du -sh /tmp /var/tmp

# 查找历史临时文件
find /tmp -xdev -type f -mtime +7 -ls 2>/dev/null

# 查看只读文件系统
mount | grep ' ro[,]'

# 查看内核磁盘和文件系统错误
dmesg -T | tail -100

# 查看用户磁盘配额
quota -u <用户名>
```

## 24. 排查结论模板

### 故障现象

服务器根分区使用率达到 100%，应用程序无法写入日志和临时文件，部分接口返回异常，服务重启失败。

### 故障确认

通过 `df -hT` 确认根分区空间已耗尽，使用 `du -xhd1` 逐级排查后发现 `/var/log` 占用了大量磁盘空间。

### 根本原因

应用程序因外部接口调用失败持续输出完整异常堆栈，同时日志轮转配置没有生效，导致单个日志文件在短时间内增长到数十 GB，最终占满根分区。

### 临时处理

暂停异常任务，安全截断确认可以清理的应用日志文件，释放磁盘空间并恢复业务服务。

### 永久修复

修复外部接口异常重试逻辑，将重复异常日志调整为限频输出，重新配置日志轮转策略，限制单个日志文件大小和保留数量，并增加磁盘使用率及日志增长速度告警。

### 验证结果

修复后持续观察磁盘使用情况，日志可以正常轮转和压缩，磁盘使用率保持稳定，未再次出现空间快速增长的问题。

## 25. 总结

Linux 磁盘空间不足排查不能只查看磁盘使用率，还需要同时检查 inode、挂载点、已删除文件、文件系统状态、用户磁盘配额和应用数据增长情况。

排查时应先使用 `df` 确认发生问题的文件系统，再使用 `du` 和 `find` 逐级定位占用空间的目录与文件。如果 `df` 和 `du` 结果差异较大，应重点检查已删除但仍被进程占用的文件以及被挂载点隐藏的文件。

处理磁盘空间不足时，应避免直接执行范围不明确的删除命令。数据库文件、容器数据卷、系统日志和业务数据都可能具有重要用途，删除前必须确认文件归属、使用状态、备份情况和恢复方式。

临时清理只能用于快速恢复服务。最终应通过日志轮转、数据归档、临时文件清理、容器日志限制、备份保留策略、磁盘扩容和容量监控等方式解决根本问题，避免磁盘空间再次被耗尽。
