# Linux 磁盘 IO 过高排查

## 1. 问题概述

Linux 磁盘 IO 过高是指服务器在一段时间内存在大量磁盘读写请求，磁盘吞吐量、IOPS、平均响应时间或磁盘利用率达到较高水平，导致应用程序读写延迟增加，甚至出现系统卡顿、接口超时、数据库响应缓慢等问题。

磁盘 IO 过高不一定表示磁盘已经发生故障。业务高峰期的大量请求、数据库批量查询、日志集中写入、文件复制、备份任务和 Swap 频繁换入换出，都可能导致磁盘 IO 升高。

排查磁盘 IO 问题时，不能只看某个瞬时指标，而要结合磁盘利用率、IO 等待时间、平均响应时间、队列长度、读写吞吐量、进程 IO、文件访问和业务任务进行综合判断。

排查的核心目标包括：

1. 确认系统是否真的存在磁盘 IO 瓶颈。
2. 确认是读取过多、写入过多，还是大量随机 IO。
3. 确认发生问题的是哪块磁盘或哪个文件系统。
4. 定位产生大量 IO 的进程、线程和文件。
5. 判断问题来自业务访问、系统换页、定时任务还是存储故障。
6. 采取限流、错峰、参数优化、存储扩容等针对性措施。

## 2. 常见问题现象

Linux 磁盘 IO 过高时，通常会出现以下现象：

1. 应用接口响应时间明显增加。
2. 数据库查询、更新或事务提交变慢。
3. 文件上传、下载、复制或解压缩速度下降。
4. SSH 登录后执行命令反应缓慢。
5. 系统负载很高，但 CPU 使用率并不高。
6. CPU 的 `%iowait` 指标持续升高。
7. 大量进程处于不可中断睡眠状态。
8. `top` 中出现较多状态为 `D` 的进程。
9. `iostat` 中磁盘 `%util` 长时间接近 100%。
10. 磁盘平均响应时间明显升高。
11. 磁盘请求队列持续积压。
12. 数据库出现慢查询、锁等待或写入延迟。
13. 日志采集、备份或批处理任务执行缓慢。
14. 容器服务同时出现磁盘读写延迟。
15. 内核日志中出现磁盘超时、重置或文件系统错误。

需要注意，系统负载高并不一定由 CPU 使用率高引起。处于不可中断睡眠状态的进程也会计入系统负载，因此磁盘 IO 阻塞可能导致 Load Average 很高，但 CPU 仍有较多空闲。

## 3. 磁盘 IO 的重要指标

### 3.1 IOPS

IOPS 表示磁盘每秒能够完成的 IO 请求数量，适合衡量大量小文件读写、数据库随机读写等场景。

在相同吞吐量下，请求越小，IOPS 通常越高。磁盘是否达到 IOPS 瓶颈，需要结合磁盘类型和存储规格判断。

### 3.2 吞吐量

吞吐量表示磁盘每秒读写的数据量，常见单位为 KB/s、MB/s 或 GB/s。

大文件复制、备份、视频处理和批量数据导入通常更容易达到吞吐量上限。

### 3.3 await

`await` 表示一次 IO 请求从提交到完成的平均等待时间，通常以毫秒为单位，包括请求在队列中等待以及存储设备实际处理的时间。

如果 `await` 持续升高，说明 IO 请求响应变慢。具体多高算异常需要结合磁盘类型、业务延迟要求和历史基线判断。

### 3.4 aqu-sz

`aqu-sz` 表示平均 IO 请求队列长度。该值持续较高时，说明大量 IO 请求正在等待磁盘处理。

队列较高不一定单独代表故障，但如果同时伴随 `await` 和 `%util` 升高，通常说明磁盘已经存在明显压力。

### 3.5 %util

`%util` 表示统计周期内磁盘处理 IO 请求的时间比例。对于传统单队列机械磁盘，`%util` 接近 100% 通常说明磁盘接近饱和。

对于 SSD、NVMe、多队列设备、RAID 和云存储，`%util` 的解释更加复杂。即使 `%util` 接近 100%，设备仍可能存在并行处理能力；也可能在 `%util` 没达到 100% 时，已经触及云盘 IOPS、吞吐量或突发额度限制。

### 3.6 %iowait

`%iowait` 表示 CPU 空闲且至少存在一个未完成磁盘 IO 请求的时间比例。

`%iowait` 较高通常说明任务正在等待 IO，但不能仅凭这一项判断磁盘一定存在性能瓶颈。还需要结合 `iostat`、进程状态和业务延迟继续分析。

### 3.7 r/s 与 w/s

- `r/s`：每秒完成的读请求数量。
- `w/s`：每秒完成的写请求数量。

这两个指标可以帮助判断当前磁盘压力主要来自读取还是写入。

### 3.8 rkB/s 与 wkB/s

- `rkB/s`：每秒读取的数据量。
- `wkB/s`：每秒写入的数据量。

通过这些指标可以判断当前主要是大量小 IO，还是大规模顺序读写。

## 4. 磁盘 IO 过高的常见原因

### 4.1 数据库读写压力过大

数据库通常是磁盘 IO 过高的主要来源之一。

常见原因包括：

- SQL 查询没有使用索引，发生全表扫描。
- 大量并发查询读取数据。
- 大批量更新、删除或插入数据。
- 事务提交过于频繁。
- 数据库缓冲池配置过小。
- 临时表落盘。
- 排序和分组操作产生大量磁盘临时文件。
- Binlog、Redo Log、Undo Log 或 WAL 写入量过大。
- 数据库备份、恢复或主从同步集中运行。
- Checkpoint 或脏页集中刷盘。
- 数据库表和索引碎片较多。

### 4.2 日志写入量过大

应用日志、访问日志、错误日志、安全审计日志和数据库日志如果写入频率过高，会产生持续的磁盘写入压力。

常见场景包括：

- 应用开启 Debug 日志。
- 异常堆栈被重复打印。
- 每个请求都记录大量详细信息。
- 多个服务向同一块磁盘集中写日志。
- 日志采集程序频繁扫描和读取日志。
- 容器标准输出日志持续增长。
- 日志轮转时进行大量压缩操作。

### 4.3 文件复制、压缩或备份任务

以下任务可能在短时间内产生大量顺序读写：

- 数据库全量备份。
- 文件同步。
- 目录打包和压缩。
- 数据解压缩。
- 镜像构建。
- 大文件上传或下载。
- 数据迁移。
- 定时归档。
- 云存储同步。
- 快照创建和恢复。

如果这些任务与业务高峰期重叠，可能明显影响在线请求。

### 4.4 内存不足导致频繁 Swap

物理内存不足时，Linux 会频繁将内存页写入 Swap，并在需要时重新读取。频繁换入换出会产生大量磁盘 IO，导致系统性能严重下降。

这种情况下，磁盘 IO 高只是表面现象，根本原因可能是内存不足、内存泄漏或应用内存配置不合理。

### 4.5 大量小文件随机读写

大量小文件读写会增加寻址、元数据更新和文件系统操作开销。

常见场景包括：

- Session 文件。
- 图片缩略图。
- 缓存文件。
- 邮件队列。
- 临时文件。
- 容器存储层。
- 海量日志分片。
- 应用频繁创建和删除文件。

机械硬盘处理随机 IO 的能力较弱，尤其容易在此类场景下出现性能瓶颈。

### 4.6 Page Cache 命中率低

如果应用需要访问的数据无法有效保留在 Page Cache 或数据库缓冲池中，就需要频繁从磁盘读取数据。

常见原因包括：

- 服务器物理内存不足。
- 应用访问的数据集远大于内存。
- 数据访问缺乏局部性。
- 大文件扫描挤出热点缓存。
- 数据库缓冲池配置过小。
- 多个服务争抢内存。

### 4.7 定时任务集中执行

多个定时任务如果在同一时间启动，可能形成明显的磁盘 IO 峰值。

例如：

- 凌晨数据库备份。
- 日志轮转和压缩。
- 数据同步。
- 报表生成。
- 文件归档。
- 缓存重建。
- 安全扫描。
- 数据清理。
- 批量 ETL 任务。

### 4.8 存储设备性能不足

如果业务的 IOPS 或吞吐量需求超过磁盘能力，即使应用没有异常，也可能出现持续的 IO 等待。

常见情况包括：

- 使用机械硬盘承载高并发数据库。
- 云盘规格过低。
- 云盘突发性能额度耗尽。
- 多个高 IO 服务共享同一磁盘。
- RAID 配置不适合当前负载。
- 网络存储带宽不足。
- 虚拟化环境存在存储资源争抢。

### 4.9 磁盘或文件系统异常

磁盘坏块、连接异常、控制器重置、文件系统错误和存储超时，都可能导致磁盘响应时间突然升高。

此时 IO 请求数量可能并不高，但 `await` 很高，进程大量进入 `D` 状态，并且内核日志中可能出现错误。

## 5. 排查前的注意事项

生产环境排查磁盘 IO 问题时，应注意以下事项：

1. 不要直接终止数据库等核心进程。
2. 不要在 IO 已经严重过载时执行全盘扫描。
3. 不要随意清理 Page Cache。
4. 不要直接删除数据库数据文件或事务日志。
5. 不要在业务高峰期执行大规模压缩或迁移。
6. 不要仅根据一次 `top` 或 `iostat` 结果下结论。
7. 应结合历史监控确定正常基线。
8. 应记录问题发生时间，并与定时任务和业务流量对比。
9. 在云服务器上应同时检查云盘 IOPS、吞吐量和突发额度。
10. 检查磁盘健康状态前，应确认工具和设备类型是否匹配。

建议先保存以下信息：

```bash
date
uptime
top -b -n 1 | head -40
vmstat 1 10
iostat -x 1 10
pidstat -d 1 10
ps -eo state,pid,ppid,comm,wchan:32 --sort=state
dmesg -T | tail -200
```

## 6. 第一步：查看系统负载和 IO 等待

执行：

```bash
uptime
```

示例：

```text
21:30:00 up 30 days, 3 users, load average: 12.50, 10.80, 8.20
```

Load Average 分别表示过去 1 分钟、5 分钟和 15 分钟的平均负载。

如果负载明显高于 CPU 核心数，应继续确认是 CPU 计算任务过多，还是存在大量等待 IO 的进程。

执行：

```bash
top
```

重点关注 CPU 行中的：

```text
%us
%sy
%id
%wa
```

其中：

- `%us`：用户态 CPU 使用率。
- `%sy`：内核态 CPU 使用率。
- `%id`：CPU 空闲率。
- `%wa`：IO 等待比例。

如果 Load Average 很高、CPU 使用率不高，但 `%wa` 明显升高，应重点排查磁盘或网络存储 IO。

## 7. 第二步：使用 vmstat 判断系统状态

执行：

```bash
vmstat 1 10
```

重点关注：

- `r`：等待 CPU 的进程数量。
- `b`：处于不可中断睡眠状态的进程数量。
- `si`：每秒从 Swap 换入的数据量。
- `so`：每秒换出到 Swap 的数据量。
- `bi`：从块设备读取的数据量。
- `bo`：写入块设备的数据量。
- `wa`：CPU 等待 IO 的时间比例。

如果 `b` 持续较高，说明存在较多正在等待 IO 的进程。

如果 `si` 和 `so` 持续不为 0，并且 `bi`、`bo` 较高，说明磁盘压力可能与 Swap 频繁换页有关。

如果 `bo` 很高，说明当前可能存在大量写入；如果 `bi` 很高，说明当前可能存在大量读取。

## 8. 第三步：使用 iostat 定位繁忙磁盘

如果系统没有 `iostat`，需要安装 `sysstat` 工具包。

执行：

```bash
iostat -x 1 10
```

常见输出指标包括：

```text
Device  r/s  w/s  rkB/s  wkB/s  await  aqu-sz  %util
sda     100  500   4096   20480   35.2    12.5   98.5
```

重点关注：

- `r/s`：每秒读请求数量。
- `w/s`：每秒写请求数量。
- `rkB/s`：每秒读取数据量。
- `wkB/s`：每秒写入数据量。
- `await`：IO 请求平均响应时间。
- `aqu-sz`：平均 IO 请求队列长度。
- `%util`：设备处理 IO 的繁忙程度。

常见判断方式如下：

- `%util` 持续接近 100%，说明设备可能接近饱和。
- `await` 持续升高，说明 IO 响应时间变长。
- `aqu-sz` 持续较高，说明 IO 请求出现排队。
- `r/s` 高表示读取请求较多。
- `w/s` 高表示写入请求较多。
- `rkB/s`、`wkB/s` 高表示吞吐量较大。

不能机械地使用固定阈值判断所有设备。机械硬盘、SATA SSD、NVMe SSD、RAID 和云盘的正常指标范围差异较大，应结合设备规格、历史基线和业务延迟要求分析。

## 9. 第四步：确认磁盘与挂载点关系

`iostat` 显示的是块设备名称，而应用访问的是文件系统目录，因此需要确认设备、分区和挂载点之间的关系。

执行：

```bash
lsblk -f
```

也可以执行：

```bash
df -hT
```

查看挂载关系：

```bash
findmnt
```

例如，`iostat` 显示 `/dev/sdb` IO 很高，需要通过 `lsblk` 和 `findmnt` 判断它对应 `/data`、数据库目录还是 Docker 数据目录。

在 LVM、RAID、Device Mapper、云盘或容器环境中，设备关系可能更加复杂，需要逐层确认：

```text
物理磁盘 → RAID 或云盘 → LVM → 文件系统 → 挂载目录 → 应用目录
```

## 10. 第五步：定位高 IO 进程

### 10.1 使用 pidstat

执行：

```bash
pidstat -d 1 10
```

重点关注：

- `kB_rd/s`：进程每秒从磁盘读取的数据量。
- `kB_wr/s`：进程每秒向磁盘写入的数据量。
- `kB_ccwr/s`：进程取消写入的数据量。
- `iodelay`：进程的块 IO 延迟。

查看指定进程：

```bash
pidstat -d -p <PID> 1 10
```

如果某个进程的 `kB_rd/s` 或 `kB_wr/s` 长时间明显高于其他进程，可以继续排查该进程访问的文件和执行的业务任务。

### 10.2 使用 iotop

执行：

```bash
iotop
```

只显示当前正在产生 IO 的进程：

```bash
iotop -o
```

以批处理模式采样：

```bash
iotop -o -b -d 1 -n 10
```

重点关注：

- `DISK READ`。
- `DISK WRITE`。
- `IO%`。
- `SWAPIN%`。
- 进程名称和 PID。

如果 `SWAPIN%` 较高，应同时排查内存不足和 Swap 换页问题。

### 10.3 查看进程累计 IO

执行：

```bash
cat /proc/<PID>/io
```

示例：

```text
rchar: 102400000
wchar: 204800000
syscr: 10000
syscw: 20000
read_bytes: 52428800
write_bytes: 157286400
cancelled_write_bytes: 0
```

重点关注：

- `read_bytes`：进程实际从存储设备读取的累计字节数。
- `write_bytes`：进程实际向存储设备写入的累计字节数。
- `rchar`、`wchar`：进程通过系统调用读写的累计数据量。

连续执行两次并计算差值，可以估算进程在这段时间内产生的 IO。

## 11. 第六步：定位高 IO 线程

一个进程内部可能有多个线程，仅定位到进程还不足以确认具体任务。

查看进程中的线程：

```bash
top -H -p <PID>
```

也可以执行：

```bash
pidstat -d -t -p <PID> 1 10
```

对于 Java 服务，可以将十进制线程 ID 转换为十六进制：

```bash
printf '%x\n' <线程ID>
```

然后结合线程栈定位任务：

```bash
jstack <PID> | grep -A 30 "nid=0x<十六进制线程ID>"
```

需要注意，`jstack` 更适合定位线程正在执行的代码。磁盘 IO 可能由异步刷盘线程、数据库客户端、日志线程或本地库产生，需要结合进程 IO、线程栈和应用日志综合分析。

## 12. 第七步：检查进程正在访问的文件

查看进程打开的文件：

```bash
lsof -p <PID>
```

只查看普通文件：

```bash
lsof -p <PID> | grep REG
```

查看某个目录被哪些进程访问：

```bash
lsof +D /目标目录
```

`lsof +D` 会递归扫描目录，如果目录规模很大，可能产生明显开销，应谨慎使用。

还可以查看进程文件描述符：

```bash
ls -l /proc/<PID>/fd
```

通过这些信息可以判断进程主要在访问：

- 应用日志。
- 数据库数据文件。
- 数据库事务日志。
- 临时文件。
- Docker 容器日志。
- 大型归档文件。
- Swap 文件或分区。
- 网络文件系统上的文件。

## 13. 第八步：检查 D 状态进程

Linux 中进程状态 `D` 表示不可中断睡眠，通常正在等待磁盘、网络存储或其他内核资源。

查看 D 状态进程：

```bash
ps -eo state,pid,ppid,user,comm,wchan:32,args | awk '$1 == "D"'
```

查看指定进程的内核栈：

```bash
cat /proc/<PID>/stack
```

查看等待位置：

```bash
cat /proc/<PID>/wchan
```

如果大量进程长期处于 `D` 状态，可能存在以下问题：

- 本地磁盘响应缓慢。
- 磁盘设备故障。
- NFS 或其他网络存储异常。
- 文件系统锁等待。
- 块设备队列严重积压。
- 内核正在等待设备完成 IO。

`D` 状态进程通常不能被普通信号立即终止。即使执行 `kill -9`，也需要等内核中的 IO 操作返回后，进程才能真正退出。

## 14. 第九步：排查内存和 Swap

执行：

```bash
free -h
```

查看换页情况：

```bash
vmstat 1 10
```

查看 Swap：

```bash
swapon --show
```

如果 `MemAvailable` 很低、Swap 使用量较高，并且 `si`、`so` 持续不为 0，说明系统正在频繁换页。

此时应继续排查：

- 哪个进程占用内存较高。
- 是否存在内存泄漏。
- Java 堆是否配置过大。
- 是否有大量匿名内存。
- 是否可以降低并发量。
- 是否需要增加物理内存。

如果根本原因是内存不足，仅优化磁盘参数无法真正解决问题。

## 15. 第十步：排查数据库 IO

### 15.1 MySQL 常见排查方向

MySQL IO 过高时，应重点检查：

- 慢查询数量。
- 全表扫描。
- 大量排序和临时表。
- Buffer Pool 命中率。
- 脏页刷盘。
- Redo Log 写入。
- Binlog 写入。
- 大事务。
- 批量更新和删除。
- 备份任务。
- 主从复制。

查看当前会话：

```sql
SHOW FULL PROCESSLIST;
```

查看 InnoDB 状态：

```sql
SHOW ENGINE INNODB STATUS;
```

查看是否存在磁盘临时表：

```sql
SHOW GLOBAL STATUS LIKE 'Created_tmp%';
```

查看 Buffer Pool 配置：

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
```

如果 SQL 没有使用合适索引，可能需要读取大量数据页，导致磁盘随机读取升高。应结合慢查询日志和 `EXPLAIN` 分析 SQL 执行计划。

### 15.2 PostgreSQL 常见排查方向

PostgreSQL IO 过高时，应关注：

- 顺序扫描。
- Checkpoint 频率。
- WAL 写入。
- Autovacuum。
- 大型排序和临时文件。
- 长事务。
- 数据库备份。
- 复制槽和归档任务。

### 15.3 Elasticsearch 常见排查方向

Elasticsearch IO 过高时，应关注：

- 索引写入速率。
- Segment Merge。
- Refresh。
- Translog。
- 大范围查询和聚合。
- 分片迁移。
- 快照备份。
- 磁盘水位。
- 节点是否承载过多分片。

数据库 IO 优化不能只通过限制进程解决，应从 SQL、索引、缓存、事务大小、刷盘策略和存储架构等方面综合处理。

## 16. 第十一步：排查日志写入

定位大型或快速增长的日志：

```bash
du -sh /var/log/* 2>/dev/null | sort -h
```

查看近期修改的日志文件：

```bash
find /var/log -type f -mmin -10 -ls 2>/dev/null
```

查看应用日志目录：

```bash
du -sh /应用日志目录/* 2>/dev/null | sort -h
```

常见问题包括：

- 日志级别设置为 Debug。
- 异常堆栈无限重复。
- 请求和响应内容全部记录。
- 大对象被序列化到日志。
- 多线程同步写日志。
- 日志刷盘策略过于频繁。
- 日志轮转时集中压缩。
- 容器日志没有大小限制。

可以采取以下优化措施：

- 调整日志级别。
- 对重复错误进行限频。
- 减少不必要的请求和响应日志。
- 使用异步日志。
- 为日志设置轮转、压缩和保留周期。
- 将日志写入独立磁盘。
- 错开日志压缩和业务高峰时间。

## 17. 第十二步：排查定时任务和批处理任务

查看当前用户的定时任务：

```bash
crontab -l
```

查看系统定时任务：

```bash
ls -l /etc/cron.d/
ls -l /etc/cron.daily/
ls -l /etc/cron.hourly/
```

查看 systemd 定时器：

```bash
systemctl list-timers --all
```

重点检查问题发生时间附近是否执行了：

- 数据库备份。
- 日志轮转。
- 日志压缩。
- 数据同步。
- 文件归档。
- 数据清理。
- 报表生成。
- Docker 镜像构建。
- 安全扫描。
- 搜索索引重建。

如果磁盘 IO 每天在固定时间升高，通常应优先排查定时任务。

## 18. 第十三步：排查 Docker 和容器 IO

查看容器资源使用：

```bash
docker stats
```

查看 Docker 磁盘占用：

```bash
docker system df -v
```

查看容器进程：

```bash
docker top <容器名称或ID>
```

容器磁盘 IO 过高的常见原因包括：

- 容器日志大量写入。
- 数据库运行在容器中。
- 容器频繁写可写层。
- 多个容器共享同一数据盘。
- 容器内执行备份或压缩任务。
- OverlayFS 产生额外写放大。
- 数据卷位于性能不足的磁盘。

应尽量将数据库、日志和大型持久化数据写入独立数据卷，避免高频写入容器可写层。

## 19. 第十四步：检查磁盘健康状态

查看内核日志：

```bash
dmesg -T | grep -iE "error|fail|timeout|reset|I/O error|blk_update"
```

也可以查看最近的内核日志：

```bash
journalctl -k --since "1 hour ago"
```

常见磁盘异常信息包括：

```text
I/O error
Buffer I/O error
device reset
timed out
rejecting I/O
EXT4-fs error
XFS error
```

对于支持 SMART 的本地磁盘，可以使用：

```bash
smartctl -a /dev/sdX
```

重点关注：

- Reallocated Sector Count。
- Current Pending Sector。
- Offline Uncorrectable。
- CRC Error。
- SMART overall-health。
- 设备温度。
- 通电时间。
- 错误日志。

对于 NVMe 设备，可以执行：

```bash
nvme smart-log /dev/nvme0
```

如果出现介质错误、设备重置、超时或坏块增长，应优先备份数据并联系基础设施或硬件维护人员处理。

## 20. 第十五步：排查云盘和网络存储

如果服务器使用云盘，应同时检查云平台监控中的：

- 云盘 IOPS。
- 读写吞吐量。
- 平均响应时间。
- 队列长度。
- 突发性能额度。
- 吞吐量上限。
- 实例总存储带宽。
- 云盘性能等级。

部分云盘采用突发性能机制。短时间内性能较高，但突发额度耗尽后性能会明显下降。这时 Linux 内部可能看到 `await` 和队列长度升高，但 IO 请求量没有明显变化。

如果使用 NFS、Ceph、GlusterFS 或其他网络存储，还应检查：

- 网络延迟和丢包。
- 存储服务端负载。
- NFS Server 状态。
- 挂载参数。
- 网络带宽。
- 存储集群健康状态。
- 客户端是否大量进入 `D` 状态。

网络存储性能问题不能只从本机磁盘指标判断，需要同时检查网络和存储服务端。

## 21. 常见处理措施

### 21.1 临时止损措施

当磁盘 IO 已经严重影响业务时，可以根据实际情况采取以下措施：

1. 暂停非核心备份和归档任务。
2. 暂停大型文件复制、压缩和解压任务。
3. 降低批处理任务并发度。
4. 限制数据库批量写入速度。
5. 降低日志级别和日志写入量。
6. 对消息消费者进行限速。
7. 将高 IO 任务错开业务高峰期。
8. 将部分流量切换到其他节点。
9. 临时扩容实例或存储性能规格。
10. 如果存在 Swap 抖动，优先降低内存压力。
11. 对异常进程进行业务确认后停止或重启。
12. 对存储故障及时进行数据备份和节点切换。

临时措施的目标是尽快降低 IO 压力并恢复核心业务，后续仍需定位根本原因。

### 21.2 优化数据库访问

常见优化方式包括：

- 为高频查询建立合适索引。
- 避免不必要的全表扫描。
- 将批量写入合并处理。
- 控制单个事务大小。
- 优化慢查询。
- 合理配置数据库缓冲池。
- 减少不必要的同步刷盘。
- 优化表结构和索引结构。
- 将读请求分散到只读节点。
- 对历史数据进行归档。
- 将备份任务安排在业务低峰期。

涉及数据可靠性的刷盘参数不能只为了降低 IO 而随意修改，应充分评估数据丢失风险。

### 21.3 优化日志系统

常见优化方式包括：

- 将 Debug 日志调整为 Info 或 Warn。
- 对重复异常日志进行采样和限频。
- 使用异步日志写入。
- 减少不必要的大字段日志。
- 配置日志轮转和压缩。
- 将日志与数据库数据分盘存储。
- 错开日志压缩时间。
- 使用日志采集系统及时转移日志。

### 21.4 优化文件处理方式

对于大文件处理，可以采用：

- 流式读取和写入。
- 合理增大单次 IO 块大小。
- 避免反复读取同一文件。
- 减少不必要的临时文件。
- 将多个小文件合并存储。
- 降低压缩任务并发度。
- 避免业务高峰期进行全量扫描。
- 使用对象存储保存大文件和历史文件。

### 21.5 优化存储架构

如果业务长期超过当前磁盘能力，可以考虑：

- 将机械硬盘升级为 SSD 或 NVMe。
- 提高云盘性能等级。
- 增加云盘 IOPS 和吞吐量。
- 将数据库、日志、备份分盘存储。
- 使用 RAID 提升性能或可靠性。
- 使用多个磁盘分散 IO。
- 建立数据库读写分离架构。
- 将历史数据迁移到低成本存储。
- 增加缓存层，降低磁盘读取次数。

## 22. 不建议直接执行的操作

### 22.1 不建议随意清理 Page Cache

以下命令不应作为磁盘 IO 高的常规解决方案：

```bash
echo 3 > /proc/sys/vm/drop_caches
```

清理 Page Cache 后，应用后续访问数据时需要重新从磁盘读取，可能进一步增加磁盘 IO，并导致业务延迟升高。

### 22.2 不建议直接修改数据库刷盘参数

降低数据库刷盘频率可能减少 IO，但也可能增加异常宕机时的数据丢失风险。修改前必须理解参数含义并进行数据可靠性评估。

### 22.3 不建议在高负载时进行全盘扫描

以下操作可能产生大量额外 IO：

- 全盘执行 `find`。
- 全盘执行 `du`。
- 运行杀毒或安全扫描。
- 创建全盘压缩包。
- 生成大型 Core Dump 或 Heap Dump。
- 对所有文件计算哈希值。

应从问题磁盘和疑似目录开始逐步缩小范围。

### 22.4 不建议直接终止 D 状态进程

`D` 状态进程正在等待内核 IO，执行 `kill -9` 通常不能立即使其退出。应优先解决底层存储或网络存储异常。

## 23. 监控与预防建议

建议持续监控以下指标：

- 磁盘 IOPS。
- 磁盘读写吞吐量。
- `await`。
- `aqu-sz`。
- `%util`。
- CPU `%iowait`。
- D 状态进程数量。
- 进程读写速率。
- Swap 换入和换出速率。
- 数据库慢查询数量。
- 数据库脏页和刷盘情况。
- 云盘突发额度。
- 文件系统错误。
- 磁盘 SMART 健康状态。
- 网络存储延迟。
- 应用接口响应时间。

监控告警应结合历史基线和业务特点设置。例如：

- `await` 连续多个周期明显高于正常基线。
- `%util` 长时间接近设备上限。
- IO 队列长度持续升高。
- `%iowait` 持续较高。
- D 状态进程数量突然增加。
- 云盘 IOPS 或吞吐量达到规格上限。
- 磁盘出现 IO Error 或设备重置。
- 数据库慢查询数量快速增长。

单个瞬时峰值不一定表示故障，持续异常和业务响应时间恶化更有判断价值。

## 24. 推荐排查流程

Linux 磁盘 IO 过高时，可以按照以下顺序排查：

1. 使用 `uptime` 和 `top` 查看系统负载及 `%iowait`。
2. 使用 `vmstat 1 10` 判断是否存在 IO 等待或 Swap 换页。
3. 使用 `iostat -x 1 10` 定位繁忙磁盘。
4. 根据 `await`、`aqu-sz`、`%util` 和吞吐量判断磁盘压力。
5. 使用 `lsblk`、`df` 和 `findmnt` 确认设备对应的挂载目录。
6. 使用 `pidstat -d` 和 `iotop` 定位高 IO 进程。
7. 使用线程级工具定位进程内部的高 IO 任务。
8. 使用 `lsof` 和 `/proc/<PID>/fd` 查看进程访问的文件。
9. 检查是否存在大量 D 状态进程。
10. 检查物理内存和 Swap 是否存在压力。
11. 检查数据库慢查询、刷盘、备份和批量任务。
12. 检查日志写入、压缩和轮转任务。
13. 检查 Docker 容器、定时任务和文件同步任务。
14. 查看内核日志和磁盘健康状态。
15. 如果使用云盘或网络存储，检查外部存储监控。
16. 采取限流、暂停非核心任务、错峰或扩容等措施。
17. 完成应用、数据库或存储层的根本优化。
18. 通过持续监控和压力测试验证处理效果。

## 26. 排查结论模板

### 故障现象

业务接口响应时间明显增加，系统 Load Average 持续升高，CPU 使用率不高，但 `%iowait` 长时间维持在较高水平。

### 故障确认

通过 `iostat -x` 发现数据盘 `%util` 长时间接近 100%，`await` 和 IO 队列长度明显高于正常水平。通过 `pidstat -d` 和 `iotop` 定位到数据库进程产生了大量磁盘读取。

### 根本原因

业务高峰期执行了一条缺少有效索引的统计查询，数据库对大表进行了全表扫描。同时，数据库备份任务正在读取同一数据盘，两个任务叠加导致磁盘吞吐量达到上限，IO 请求大量排队。

### 临时处理

终止确认无业务影响的统计任务，暂停数据库备份，并对相关接口临时限流，使磁盘 IO 和接口响应时间逐步恢复正常。

### 永久修复

为统计查询建立合适的联合索引，优化查询范围和分页方式，将数据库备份调整到业务低峰期，并将备份目录迁移到独立磁盘。同时增加磁盘 `await`、队列长度和数据库慢查询告警。

### 验证结果

优化后使用相同数据量进行压力测试，SQL 扫描行数明显下降，磁盘平均响应时间和队列长度恢复正常，业务接口响应时间满足预期。

## 27. 总结

Linux 磁盘 IO 过高排查的关键是先确认系统是否真的受到 IO 限制，再定位具体设备、进程、线程、文件和业务任务。

`top` 和 `vmstat` 可以帮助判断系统是否存在 IO 等待，`iostat` 可以定位繁忙磁盘，`pidstat` 和 `iotop` 可以定位高 IO 进程，`lsof` 和 `/proc` 可以进一步确认进程正在访问的文件。对于数据库、容器、云盘和网络存储，还需要结合对应系统的监控和日志继续分析。

磁盘 IO 高可能是业务访问量增加，也可能是慢查询、日志爆发、备份任务、Swap 抖动或存储设备异常造成的。不能只根据 `%util` 或 `%iowait` 某一个指标直接下结论，而应结合响应时间、队列长度、读写类型、设备规格和历史基线综合判断。

临时处理可以通过暂停非核心任务、降低并发、限制日志和错峰执行等方式快速缓解压力。长期解决方案则需要从 SQL 和索引优化、缓存设计、日志管理、任务调度、内存容量和存储架构等方面进行改进，并建立持续的磁盘性能监控和容量规划机制。
